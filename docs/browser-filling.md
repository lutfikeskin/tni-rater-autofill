# Browser filling and carrier page changes

Read this when changing control discovery, matching, repeated rows, helper actions, or navigation.

## Execution

[sidepanel.js](../sidepanel/sidepanel.js) builds a plan and injects [pagekit.js](../src/content/pagekit.js) into the quote tab's frames. Progressive runs in `MAIN` world to access ExtJS. Pagekit is a classic script without imports; bump its `__raterKit.version` when changing the injected API.

[field-key.js](../src/content/field-key.js) loads before both pagekit and the recorder, in each script's world. A Duck Creek field (Progressive) is keyed by its data-model name (`ref:<fieldref>`), so an agent edit stays with its question when Progressive renumbers; an edit saved by an older build under the question id still protects that field. Element names and ids keep their keys; a Progressive per-vehicle question row past the first gets `@<row>`. Checkboxes that share one name across rows, with the row only in their id (AmWINS' Vehicle Coverages), get `name#<row>` on every row; a plain name saved by an older build protects all of that name's rows. Anonymous controls use a versioned structural key anchored to their container and row, so repeated carrier fields do not share manual-edit protection or fill history. Labels and current values do not determine those keys.

The fill loop collects controls, assigns rules, applies answers, waits for the page, rereads values, and rescans. Server-backed pages generally fill one answer per round; a carrier with `batch: true` fills a visible round before settling. Enable batching only with evidence about that carrier's behavior.

A carrier rule finds its question by what it is, never by a remembered question id: Progressive renumbered every question on 2026-10-07, and ids kept from before put answers into other questions (Business Name got the trucker type). Its field's data-model name (`field`: Duck Creek's `fieldref`, such as `RiskInput.VIN`, on any page) comes first, and the rule's wording (`ask`/`label`) is then a check: a field found by name whose question reads differently is answered and flagged for the agent (`reworded`). A data-model name missing from the page while its wording is there is a probable rename (`renamed`): that field is left with the agent. Otherwise the question's text on the rule's page (`ask` exact, or `label`), never a field another rule knows by name, after an anchor question when the text repeats (`askAfter`: the business and the owner's "City"), of a given field kind when two kinds share it (`control`), or the list offering a given answer (`withOption`). A step that only has an id finds nothing, and a known question that isn't found stays with the agent rather than falling back to a looser label rule. Each answer records what found its field (`how`). Selectors and known options come next, then label fallbacks. Rows of one question share an id on the page, which is compared with the page itself only; the active vehicle index alone does not prove which visible column belongs to it. A label fallback never takes one of several rows of a question, or a question the plan answers per vehicle; ambiguous rows (two vehicles that read the same) stay with the agent. Reacquire controls after redraws and verify the retained value. A list that is still empty when its answer comes (one filled in by another answer, such as Progressive's cargo commodities after their category) gets a few seconds to load before nothing matches. Retries are bounded; do not bypass acceptance checks to improve completion counts.

## Review and navigation

- Unknown fields are marked; supported fields can still fill. Missing data, failures, differing retained values, confirmations, and blocked helpers contribute to the review report. A field drawn without a caption is named there after its rule. A helper that opens the next page (the vehicle tile) leaves that page's questions to its own fill; none is reported as the earlier page's.
- Unfamiliar fields block advance when required or unanswered. Optional prefilled unknowns do not always block; explicit optional/ignored rules and agent dismissals also affect this behavior.
- Agent edits are protected; an edit during filling interrupts the run. Keep that protection across retries and AI responses.
- Trusted native input/change events identify the exact control the agent answered, including a dropdown selection made after a long delay. A prefilled or page-generated value alone does not resolve missing intake data; explicit review notes still require confirmation.
- Helper actions use prerequisites and quote/entity scope. A helper whose button shows only once the page took an answer can name that answer (`nudge`: Progressive's Done with this coverage after the cargo commodity): with everything else ready and no button, the answer is picked again, once. Continuation uses a separate carrier `advance` pattern and the panel setting, with unresolved blockers and pending AI approvals holding it, and never on a page the plan expects questions on that shows none yet and where nothing was done (still drawing).
- A carrier's `stopPages` are pages where the carrier has stopped the quote (Progressive's `DeclinationNotice`: the client already has a Progressive commercial auto policy). The panel shows the carrier's note above both steps, disables Fill this page, and runs no fill, follow-up, helper, Continue, or Luna request there; the page kit refuses them too. The note states the carrier's reason for this client, and each arrival (including a reload) is logged as a `fill_run` with the blocker `stop: <page>`, only once the tab is shown to hold this intake's quote (the layout-readiness evidence); before that the panel says the page may belong to another client.
- `NEVER_CLICK` and `NEVER_ADVANCE` restrict dangerous actions. Save & Continue is a specific supported continuation exception, not permission for arbitrary Save, Submit, Bind, Buy, Finish, Delete, or report-order actions.
- On one-address applications, the panel checks that the visible step signature changes after continuation. A click is not proof of navigation or of a generated document.

## When the carrier changes

A new question can become unfamiliar; a missing option or rejected answer can become a fill failure. When a known field looks renamed, or at least five questions and 40% of a page are unfamiliar, the fill reports `pageChanged`: the panel says the carrier seems to have changed the page and Continue waits. A renumbering leaves Progressive's questions found (`npm run e2e -- --fixtures --renumber` replays every layout with shifted ids); reworded text or a renamed data-model field leaves that question unfamiliar, never answered as another. Layouts record each field's `ref` (data-model name) since 0.9.9, so a rule can move from text to `field`. Layout capture and rule-coverage reports provide evidence for review. This does not reliably detect a changed meaning under the same data-model name or every changed conditional branch.

Capture the affected scenario and its predecessor answers, classify mapping versus control versus semantic changes, then update a scrubbed fixture and expected outcome. Do not infer applicability merely from a field's presence or absence in one saved page. Use [corrections](corrections.md) for an observed failure and [new carriers](new-carrier.md) for expanded scenario support.
