# Browser filling and carrier page changes

Read this when changing control discovery, matching, repeated rows, helper actions, or navigation.

## Execution

[sidepanel.js](../sidepanel/sidepanel.js) builds a plan and injects [pagekit.js](../src/content/pagekit.js) into the quote tab's frames. Progressive runs in `MAIN` world to access ExtJS; AmWINS and GEICO run in the extension's isolated world (`worldFor`), which shares the page's DOM, open shadow roots included. Pagekit is a classic script without imports; bump its `__raterKit.version` when changing the injected API.

[field-key.js](../src/content/field-key.js) loads before both pagekit and the recorder, in each script's world. A Duck Creek field (Progressive) is keyed by its data-model name (`ref:<fieldref>`), so an agent edit stays with its question when Progressive renumbers; an edit saved by an older build under the question id still protects the field with that number, and while such a key is kept no answer already on a Progressive field is replaced (the number may be from before a renumbering, and the corrected question has a new one): one that differs from the intake is left and flagged for the agent. A GEICO field takes the same road (field key version 5, `dataName`): GEICO draws a question as `Id_<Name>_<render number>` and renumbers it on every redraw (a new step or unit form, an answer that reveals follow-ups, Recalculate), so it is keyed `ref:<Name>` from its name, else its id (a radio option's id adds its digit and `-shadow`, the VIN box `maskedField`), and a checkbox group's box (`checkbox-Id_<Name>_<n>-<Box>`) `ref:<Name>.<Box>` (`ref:AddFilings.MCS90`). GEICO's coverage lists (Quote & Coverages) have only an id, with a new UUID on every render and Recalculate: a vehicle's row is keyed by the coverage its id ends in and its place among that coverage's rows (`cov:COMP#2`; a vehicle above gaining or losing that row moves it), a policy-level list by its `[for]` caption without its tooltip (`cov:liability coverage`); a caption reading like a vehicle or an amount (a year, a VIN, a `$`) keeps the raw id, so no key carries a vehicle's year, make, model, VIN or premium. Other element names and ids keep their keys; a Progressive per-vehicle question row past the first gets `@<row>`. Checkboxes that share one name across rows, with the row only in their id (AmWINS' Vehicle Coverages), get `name#<row>` on every row; a plain name saved by an older build protects all of that name's rows. Anonymous controls use a versioned structural key anchored to their container and row, so repeated carrier fields do not share manual-edit protection or fill history. Labels and current values do not determine those keys.

Controls are read through open shadow roots in page order (a shadow root's controls where its host is). GEICO's design-system controls are read as the page draws them. A `<gds-radio-button>` keeps its `<input type=radio>` alone in its own shadow root under a host of the same name: the pick is the host's `checked` attribute (an option picked earlier can keep its input checked), an option is clicked only when its host isn't checked, a stale input unchecked first, and the wait for the page also counts changes of the hosts' `checked` and their group's `active-index`. Its question is the `[slot=legend]` part of the nearest element holding every option host, without its `gds-tooltip`; an option's words are its host's `[slot=label]` (Pay In Full for `GEICO_PP_1Pay`); two groups with one data-model name (the two pay-plan lists) stay two questions. A `<gds-button>` keeps its words in the page and only `<slot>`s in its shadow `<button>`: a button reads as its own text, else its slotted text, else, inside a button host's shadow root, the host's (`buttonText`), and a disabled host disables it. A select2 list (its own `<select>`, hidden by select2, with select2's box after it) is answered the way the agent answers it, and marked on that box: the box opened with a left-button mousedown, the option's text typed in the list's search box (on a list taking several, the box inside the list's own), and the one result reading exactly that text clicked; a list that shows it no time or several times when it's typed is the agent's ("the list didn't show … when it was typed; pick it yourself"), and on a list taking several a pick the answer doesn't name is taken off first with its ×. GEICO takes only select2's own pick, never a change set on the hidden `<select>` (FL live run 6, 2026-10-21: the commodity set there showed, but GEICO took none and never asked for the cargo limit; the business description set so was refused at Next). A `search-select` rule (AmWINS' classification, whose results come from its server) types its `search` words instead and picks the one result reading its value, else the one result holding it. A list taking several choices (the cargo commodities: a `<select multiple>`) gets exactly the answer's options, named by their texts joined by "; " (as it reads back), each of which must be offered and enabled (else "no option matches" and nothing is picked; an option whose own text has "; " in it is one pick), is failed when the page doesn't keep the picks, and agrees with the same picks in any order (W43-23); an AI suggestion the agent approves there is one option; a hidden, disabled or empty-value stand-in option (each coverage list starts with one repeating its choice) gives way to a real option reading the same. The street box, a search input with its own suggestion list (`aria-autocomplete=list`, `aria-controls`, not select2's filter box), is a question; other search boxes aren't. An `address-suggest` answer types the whole address and picks the first new suggestion for it: Google's (`.pac-item`) with its house number, any other with the same leading house number and, when both show one, the same ZIP after the state (another town's same street is not it). GEICO's suggestions are `<gds-dropdown-list-item type="address">` items in its address wrapper's shadow root, read as list items, not options (GEICO's script; the open list was never captured). Suggestions shown but none for the address leave the street (`fallback`) for the agent: "none of the page's address suggestions has the intake's house number and ZIP". With `checkNumber` (GEICO's street), what the fill left in the box stays the agent's on later fills while the box still holds it ("no address suggestion was picked for it"), and a street the page filled itself agrees only with the intake's house number. An `aria-label` written as markup (tags, `**`) is read as its text, and a field without a label, or with one of no letters (an amount box showing only `$`), is named by its humanized data-model name ("give year"), never its render number. GEICO's spinners (`#page-load`, `#extendedWaiting`) count as the page being busy. A text box showing only its input mask (`MM/DD/YYYY`, `__/__/____`, a VIN's underscores: `MASK_ONLY`) is empty: it is filled, and the mask is never reported as the page's own answer (FL live run, 2026-10-21: the owner's date of birth and the VIN were left as differing from the intake). A list with one distinct option (GEICO's collision row lists "Not Included" twice until its comprehensive is chosen) is still loading: its answer waits up to six seconds for the rest (FL live run 2, 2026-10-21: two collision rows failed before GEICO drew their deductibles). A rule's `waitFor` (a data-model name; plan.js resolves it per unit) holds its answer while that question is on the page unanswered, or not drawn yet, for up to eight seconds, a round every 0.4 s: GEICO's vehicle form, with a VIN, waits for the decoded year, since the decode redraws the form and clears the type, distance and personal use given before it (FL live run 2: the Cascadia's Tractor was cleared three times; FL live run 3, 2026-10-21: the year is drawn only by the decode, and the type given before it was cleared). Once the question it waited for is answered, the fill waits for the page to be quiet for 0.8 s before giving the held answers (the decode redraws the type list a moment after the year). One still waiting when the fill's rounds run out is reported failed ("the page was still working on this question"). A question waited for the whole eight seconds isn't waited for again: one on the page, in that document; one never drawn, on that form (a VIN GEICO doesn't decode leaves the year empty for the agent). With nothing more to do, a fill that filled something with such a question's step on the page looks once more: it waits for the page to be quiet (0.8 s, up to eight seconds) and reads it again, so an answer a late redraw cleared is given again (`retryOnce`). The recorder reads the same way: shadow-root controls in page order, a radio's pick from its host once the host shows it, a `<gds-button>` click by its slotted words, and the street box.

The fill loop collects controls, assigns rules, applies answers, waits for the page, rereads values, and rescans. Server-backed pages generally fill one answer per round; a carrier with `batch: true` fills a visible round before settling. Enable batching only with evidence about that carrier's behavior.

On a one-address application the kit reads the step on screen (`stepKey`, exported as `step`): AmWINS' visible headings; on a page with a step progress bar (GEICO's `<gds-progress-bar>` parts), the one part under way (value between 0 and 100), and only while `document.title` names it too. The title and the form were seen to be one step's while the bar was another's mid-redraw (FL capture 007): then no step is read, and a fill whose plan has rules kept to steps does nothing there. Checked at every round, it halts ("The step on screen could not be read (the progress bar and the page title disagree): fill again once the page settles.") and reads nothing for its report: no unfamiliar or required items, marks, `pageChanged` or Continue, and `report.stepKey` is `''`. Unlike other halts it doesn't pause automatic filling (`report.stepUnread`), and the panel's report doesn't say it does: an automatic fill that comes back so is tried once more about 1.5 s later (with automatic follow-ups on, while the tab is still on that page and intake), and not again until a fill reads a step; a fill the agent asked for isn't retried. Luna is asked nothing about it. A fill that began on a step it read and then reads none ends as on the agent's Next (below). The recorder reads the step the same way. On a page with a progress bar a fill ends when the step on screen changes (the agent's Next): nothing more is given or clicked, nothing on the new step is marked or reported, Continue is not clicked, and the report is filed under the step the fill started on (`report.stepKey`); the new step gets a fill of its own.

A carrier rule finds its question by what it is, never by a remembered question id: Progressive renumbered every question on 2026-10-07, and ids kept from before put answers into other questions (Business Name got the trucker type). Its field's data-model name (`field`: Duck Creek's `fieldref`, such as `RiskInput.VIN`, or GEICO's name stem, such as `GiveYear`, on any page) comes first, and the rule's wording (`ask`/`label`) is then a check: a field found by name whose question reads differently is answered and flagged for the agent (`reworded`); one we leave as the page has it (`ignore`, `verifyOnly`, which can depend on the unit: GEICO's year, make and model when the intake has the VIN GEICO decodes) becomes a check item. A name is looked for (and keeps text rules off its field) on any page except where the rule is fenced off: Progressive's trailer pages carry the vehicle's names, so the vehicle's rules have `notPages` (the trailer pages) and the trailer's `pageOnly` (Add Trailer, or Rates for its row). On a one-address application whose steps share names (GEICO's `GiveFirstName` is the owner on Business & Owner Info and a driver on Drivers & Incidents), a rule names its steps (`steps`, against the step read from the page), and a rule for one form of a step names a question only that form asks (`whenShown` / `unlessShown`: `{ field, label?, unit? }`, a field with that data-model name on the page and, with `label`, a question matching it: GEICO's vehicle, trailer and driver forms); a rule that isn't live there neither answers nor claims a field, and a label rule kept to steps is a known question, as one kept to pages is. A data-model name missing from the page while its wording is there is a probable rename (`renamed`): that field is left with the agent. Otherwise the question's text on the rule's page (`ask` exact, or `label`), never a field another rule knows by name, after an anchor question when the text repeats (`askAfter`: the business and the owner's "City"; a field found by name needs no anchor), of a given field kind when two kinds share it (`control`; a choice or yes/no answer never goes into a text box), or the list offering a given answer (`withOption`). A step that only has an id finds nothing, and a known question that isn't found stays with the agent rather than falling back to a looser label rule. Each answer records what found its field (`how`). Selectors and known options come next, then label fallbacks. Rows of one question share an id on the page, which is compared with the page itself only; the active vehicle index alone does not prove which visible column belongs to it. A label fallback never takes one of several rows of a question, or a question the plan answers per vehicle; ambiguous rows (two vehicles that read the same) stay with the agent. A repeated selector rule can name a row's witness instead (`witness: { selector, path }`, resolved per unit by the plan): among the controls its selector finds, the step takes the one whose row (the nearest ancestor holding a control matching the witness selector, which must be the only one there) shows the unit's value, letters and digits compared; AmWINS' vehicle rows are each found by their VIN this way, since Import Valid Records draws them in its own order. No row showing the unit's value (the import hasn't landed or rejected its VIN; the intake has no VIN for it), or two rows showing it, gives the unit no row: its answers stay the agent's, with one note naming the unit ("the row for vehicle 2 (its VIN) wasn't found") and never its VIN, and the rows the rule chooses among are known questions, never unfamiliar ones. A row showing a value no intake unit has (a vehicle on the quote the intake doesn't list) is never answered or changed: it is one check item named by its place ("Vehicle row 4 on the page"), never its value, and Continue waits for the agent to remove the row or explicitly dismiss that check to keep it. Its opaque acknowledgement key contains no VIN, survives redraws, row reordering and unrelated application steps without visible witness rows within the current document, and does not carry over to a different VIN or a new document. Removing an extra identity while witness rows are visible, then re-adding it, requires new confirmation. Duplicate extra rows each require confirmation bound to that DOM row; changing their count or redrawing those ambiguous rows requires new confirmation. Reacquire controls after redraws and verify the retained value. A list that is still empty when its answer comes (one filled in by another answer, such as Progressive's cargo commodities after their category) gets a few seconds to load before nothing matches. Retries are bounded; do not bypass acceptance checks to improve completion counts.

## Review and navigation

- Unknown fields are marked; supported fields can still fill. An unfamiliar question that went away during the fill (hidden by an answer) is not reported. Missing data, failures, differing retained values, confirmations, and blocked helpers contribute to the review report. A field drawn without a caption is named there after its rule. A helper that opens the next page (the vehicle tile) leaves that page's questions to its own fill; none is reported as the earlier page's.
- The kit marks the fields it handled on the page (`mark`, `COLORS`; the title starts "Rater Autofill:"): an intake answer, or one worked out from it, solid green; a TNI standard (a plan step with `standard`, rule `source: 'standard'`) solid blue, so the agent can tell assumptions from intake facts; one left for the agent (missing data, a check item, including a standard to confirm in review mode, an unfamiliar or required question) dashed amber; one it couldn't fill dashed red; an AI answer solid purple. A follow-up fill keeps the marks of answers already in (`keepMarks`); `clear` removes them all. The page list's key (the **i** in its title, `key-btn`: **Marks on the rater page**) shows the same colors (`--mark-*` in [sidepanel.css](../sidepanel/sidepanel.css), which a pagekit test keeps equal to `COLORS`).
- Unfamiliar fields block advance when required or unanswered. Optional prefilled unknowns do not always block; explicit optional/ignored rules and agent dismissals also affect this behavior.
- Review-mode standard choices require confirmation even when the carrier preselected a different answer. The retained value is preserved; Continue waits until the agent acknowledges that field.
- The registered-name check (`businessNames`, Progressive's USDOT lookup): while the page shows a registered business name that isn't the intake's, a step with `businessNames` is not answered; it is the agent's (`noData`, `reviewOnly`, "The DOT lookup business name differs from the intake"). When that name shows only after such an answer went in (Progressive draws it right after "belongs to the business" Yes), the answer stays on the page but moves from `filled` to `noData` with the same note and is marked amber, so Continue waits. The kit checks this each round, at the end of the fill and again after the wait before Continue (`identityAfterAnswer`), where a move adds a `needs you:` blocker and Continue is not clicked. A field the agent edited is theirs and is left alone. An answer the page marks invalid is normally given again, at most twice; one the identity check left to the agent is not, nor a `keepChoice` answer this fill didn't give. Those are flagged failed and left as they are.
- A step with `labelHas` (words from the intake) is answered only when its question's own text shows each of them as whole words; otherwise it is the agent's, with `labelNote` (GEICO's "Is this the customer's business?" under its USDOT record: Yes when the record shows the intake's house number, every word of its street name and ZIP; TNI, FL live run 5, 2026-10-21, W43-24).
- Agent edits are protected; an edit during filling interrupts the run. Keep that protection across retries and AI responses. The recorder is paused while the kit puts answers in (a fill, an AI apply), so the kit's own edit guard (`guardEdits`: a trusted input/change within 2 s of a trusted gesture on that same control: the control, a radio of its group, its label (`label[for]` or a wrapping label; for a radio, the label of any radio in its group), its ExtJS trigger wrap, a detached dropdown option resolved to its ARIA owner or the control focused when the gesture occurred, or an element holding no other control; through open shadow roots the event's own target counts (`composedPath()[0]`), and a gesture on a design-system option (GEICO's radio host, its words or its shadow root) is on that option's radio; an agent click elsewhere just before the kit's own radio or checkbox click is not an edit) catches the edit, protects its key and halts; the guard stays on through the wait before Continue, so an edit there stops the Continue and the halt reason is a blocker (`advanced` is recorded only once the click went out). The same guard runs during an AI apply (`answer()`): the edited question keeps the agent's answer and the answers still to come are refused with that reason (each item of an edited question carries `protected: true`, and an edited question that was not among the answers gets a protected item of its own; the panel adds those keys to the agent's protected keys, as after a fill). On a page with several frames the panel keeps guards active in every frame for the full AI apply and sends one answer at a time to its originating frame. It checks all frames between answers: an edit in a frame whose answers are still to come or have already finished protects that question and refuses every remaining answer. Every dispatch requires its original guard session; a replaced document or changed intake context stops the remaining answers. Trusted edits caught before the apply ends are saved under the original intake fingerprint, tab, and vehicle/driver/page scope even if the panel has switched away; returning to that quote or reloading the panel restores those keys without storing answer text. Replacing the intake retains these separately scoped records; explicit Clear erases the current intake's records and cancels its late guard writes, while another intake's in-flight edits remain protected. These records share the browser/extension session boundary described below. The guards are released when the apply finishes, including transport failures. When the pause ends, the recorder reports the agent's own edits made meanwhile as theirs (a trusted value still on its control, a question the fill revealed included) before taking the new baseline; while paused it counts a trusted input/change only within 2 s of a trusted gesture on that control (the same targeting as `guardEdits`, so the gesture of an agent edit that started a follow-up fill does not claim the fill's click on another radio), since the kit's own click on a radio or checkbox fires trusted input/change too; the extension's own answers and the questions they revealed are not reported (the panel logged the fill, and the fill answered them).
- Replace existing answers (`overwrite`) replaces a value that differs from the answer; a control that already holds the answer is kept, so no event fires on it (`sameAnswer` in the kit; FL live run 4, 2026-10-21: each Fill on GEICO's Quote & Coverages set 9–12 coverages again to the values they had, once right after Recalculate). An `address-suggest` box agrees with any address, so Replace still retypes it. A choice rule with `keepUnlisted` whose answer the list doesn't have, while the list holds the page's own choice, keeps that choice: it is kept, with a check ("The page's list has no "<answer>" (<rule>): its "<choice>" is left as it is. Check it."), not a failure; with no choice of the page's, or with its OTHER (no city), it fails as before (GEICO's cities for the ZIP: TNI, 2026-10-21, W43-35).
- Trusted native input/change events identify the exact control the agent answered, including a dropdown selection made after a long delay. A pick in a select2 list (GEICO's year, make and model among them) sends only select2's own jQuery events, no native one, so neither the edit guard nor the recorder sees it as the agent's (FL live run 6, 2026-10-21: the agent's commodity pick was logged as the page's). A prefilled or page-generated value alone does not resolve missing intake data; explicit review notes still require confirmation.
- Helper actions use prerequisites and quote/entity scope (vehicle, trailer, driver). A click alone is not a result: a helper with `verify` is done only once its result shows (`premium`: a total premium and no stale-rates text, such as GEICO's "Quote $… Due Today $… Total" with no "$ --.--" or "Please Recalculate"; `gone`, `cargoClosed`, `glClosed`: Progressive's General Liability section closed with its row keeping the limit; `revealed`: a question appeared or an answer changed since a snapshot taken as the button was clicked, which is how Progressive's Lookup VIN and Verify USDOT and AmWINS' Import Valid Records count, since the page redrawn with the same questions and answers is no result; `{ appears: '<selector>' }`: more of that selector than before the click), else it is unclicked and reported as not verified. A `revealed` helper with `shownBy` (Progressive's Lookup VIN: the decoded year, make and model, all answered; Verify USDOT: any of the USDOT record's questions, including the no-record branch's 60-day question) whose result already shows for the unit's value on the page (the agent ran it before Fill; the value is the intake's and this fill didn't type it) is done without a click (reported with `alreadyShown`, no follow-up fill), even when the lookup button is absent or disabled; its prerequisites still hold. A click that redraws that result unchanged counts too. A `revealed` or `appears` helper is tried twice more in the same fill; then it stays blocked and the agent is told to do it by hand. A helper that loads a view is the exception (below): clicked once. A helper without `verify` counts on click. A helper kept to a container (`within`: GEICO's add icon in one list's add row, not the incidents' list below the drivers) is found and clicked only there, and says it is unfinished only where that container is on screen (one address draws the unit's form in the list's place). With `moveOn` too, a Next inside that container may be clicked (GEICO's chooser behind Add Vehicle or Trailer, whose Next opens the unit's form and leaves no step): it is checked against `NEVER_ADVANCE` instead of `NEVER_CLICK`, so Cancel, Save or Discard there stay off limits, and nowhere else is a Next a helper. A helper whose click draws a new view (`loads`: GEICO's add icons and the chooser's Next) is clicked, once it is due, only on a page that has been quiet for 1 s (a page that changed meanwhile is read again first), its page may load for up to a minute (`LOAD_MS`; past that the fill stops: "The page was still loading after a minute"), and its view is waited for up to 20 s once the page is quiet (`LOAD_RESULT_MS`, a `revealed` result). It is never clicked a second time: one whose view never shows is the agent's ("Clicked once, but the page never showed what it opens"). FL live run 4, 2026-10-21: GEICO drew the chooser a moment after "+" with no spinner, the fill clicked "+" three times in 1.4 s, and the adds it queued kept GEICO's spinner up for a minute. A button the carrier refuses while a required question is empty (`waitRequired`: Progressive's bill plan, Recalculate, Print) waits for it and names it. A helper kept to steps of a one-address application (`steps`) is clicked, held open or reported missing only there (GEICO's Quote & Coverages helpers). A helper with `whenClear` waits until the fill has left nothing on the page for the agent (no needs-you, failed or check item, no kept answer that differs, no empty question it listed as unfamiliar; `why`: "nothing left for you on the page"): GEICO's Recalculate, View More Payment Plans and Print Quote Proposal (TNI, FL live run 4, 2026-10-21); the last two also need a current premium (`needsPremium`). GEICO's Recalculate (TNI, 2026-10-21, W43-31) is clicked once a quote (`once`), and only on a page that has been quiet for 2 s (`quietMs`, as a `loads` helper waits 1 s; a page that changed meanwhile is read again first); its rating may take up to a minute. It keeps answers (`keepAnswers`): as it is clicked, the kit notes each answer on the step the fill gave (and the page still shows) or the agent gave, by key and place (`key#n`), and once the premium shows it reads each again. When none changed, it reads them every half second until 15 s after the click (`KEPT_WATCH_MS`: GEICO drew its own values 9 to 14 s after the fill's click in FL run 6), so View More Payment Plans and Print wait for that; a change found then is handled as one at once, after 1 s of quiet. An agent edit, another page or another step ends the watch. One of the fill's that the page changed is put back once and marked failed ("… changed this answer when it recalculated, and the fill put it back: click Recalculate yourself, then check the answer is kept"); one of the agent's is left as the page shows it and marked failed ("answer it again, then click Recalculate yourself"); and an item without a field says the premium may not be for the answers shown. Only a changed answer's own entry (its step, key and label) leaves `filled` or `kept`; another field with its key keeps its own (GEICO's two pay plan groups share one). Those failed items hold every later helper (`whenClear`), and the fill never clicks Recalculate again: a `once` helper isn't due again after later answers (`needsRecalculation` below), and one whose premium never shows is failed ("… click Recalculate yourself") rather than tried again (FL live run 6, 2026-10-21: after each Recalculate an earlier version clicked after every answer, GEICO drew the coverages again with its own choices, liability and UM back to $750,000, road service declined, cargo $5k, and the fill's and the agent's unsaved choices were lost; after each the agent clicked, it kept what the page showed). A choice rule with `whenOffered` whose option isn't shown yet (GEICO's 11 Payments, behind View More Payment Plans) waits instead of failing, tried again each round; never offered by the fill's end it is the agent's ("The page doesn't offer … here: pick it yourself."), unless another rule for the same question answered it, a `whenClear` helper is still waiting on the agent, or a `needsPremium` helper on the step is still to click while the premium isn't current (GEICO hides View More Payment Plans until the quote is recalculated). A rule with `orMost` (`{ count, one, after, name }`: GEICO's pay plan, TNI, 2026-10-21, W43-32) whose option is still not offered once its `after` helper was clicked picks instead the offered option with the most (`count`, a pattern whose first group is the number; `one`, an option that counts as 1: Pay In Full), and its filled item carries `said` ("The page doesn't offer "11 Payments" here: the fill picked "9 Payments", the plan with the most payments GEICO offers."), which the panel shows with the step's report. When an earlier fill clicked the helper, the page may have drawn fewer options since: the kit picks only the option the page already shows as its choice, so a later fill (after Print, or Fill this page) agrees with the 9 Payments the first picked, and otherwise the question is the agent's. One that waits for stale rates (`needsRecalculation`) is due again after each later answer the fill gives on its step (Progressive's Recalculate; never a `once` helper, GEICO's): it leaves the clicked set and is reported in `invalidatedActions`, which the panel drops from its helper records, as after an answer on Progressive's Rates. A helper the agent does by hand (`missing`: its needs-you item) can hold later helpers (`heldBy`) until it is settled: its button back on the page (`resolvedBy`, the Add NTL link after NTL was removed) or a page the agent has been to since (`settledByPages`, a page whose visit settles the item; no carrier uses it since Progressive's General Liability became automatic on 2026-10-20). A helper the fill didn't click is reported in `blocked` with what it waits for: `why` in ids and paths (the usage log's `button:` blockers) and `waits` (the same, by kind: fields, helpers, pages). The panel doesn't list them: a question one waits on is already a needs-you item, and the fill clicks the others in turn. A helper that waited only for answers the page now shows, and whose button the page took away before it was clicked, is done without a click, as one already shown is (`alreadyShown`: "done by the page itself"), so it isn't left waiting and a helper that follows it isn't held (SC 2026-10-19: Progressive looked a second vehicle's VIN up by itself once it was typed). Progressive's trailers follow the vehicles: Add Trailer once every vehicle's lookup is done, the trailer tile, then Add Trailer. A driver or trailer counts as entered once Progressive took its page (its list comes back from Add Driver or Add Trailer); opening it, or answers filled there alone, don't count. On the vehicle list a vehicle counts as added (its lookup and Add Vehicle done, also when the agent ran the lookup) once the agent has come back to the list from that vehicle's pages (`vehicleReturned`, `unitArrival`) and the list shows its VIN, so Add Vehicle is never clicked for it again. The VIN alone isn't enough: the list also shows the vehicles the USDOT lookup found, which are on the quote only once added. A VIN not shown proves nothing. A trailer is checked against the list itself, which shows each unit on the quote with its VIN: its VIN there means entered, and a list showing the vehicles' VINs but not the trailer's means not (back by Back or the top menu). The pick goes in through the AI's guarded path: `answerEdits` begin with a token, `decisionSnapshot`, the one field that matches the row's key and label (else "The page changed: answer it on the page."), the choice still offered, then the kit's `answer(..., { stopSteps, by: 'agent' })` in that frame, which marks it the agent's ("your answer, from the side panel"); the recorder is paused meanwhile, and edits caught are kept (`persistGuardedEdits`). The field joins the agent's keys for the page's edit scope, as their own edit there does, so no fill changes it and Continue doesn't wait on it; it is logged as the agent's `field_change`. A pending AI pick for the field becomes the agent's; a plain suggestion is dismissed. Nothing is picked while a fill runs, on another tab or page, or without an intake, and there is no Undo: the agent changes it again in the row or on the page. A typed answer, or one the panel may not answer, gets Show on page instead ("Change it on the rater page"), where the agent's answer then stays theirs.
- `NEVER_CLICK` and `NEVER_ADVANCE` restrict dangerous actions, discarding a form (GEICO's Discard Changes and "Yes, please discard."), ordering reports and signing (`sign`, `signature`, `esign`, `e-signature`) among them; the words are literal. Links in a step progress bar (GEICO's `#progressIndicator`) open their step and are never a helper or a Continue; an icon the keyboard reaches without a role (`[data-testid][tabindex]`, GEICO's add icons) can be a helper, never a Continue. Save & Continue is a specific supported continuation exception, not permission for arbitrary Save, Submit, Bind, Buy, Finish, Delete, or report-order actions. GEICO's `advance` (TNI, FL live run 3, 2026-10-21) is Next or Save and Continue on Business Class & USDOT, Business & Owner Info, Vehicles, Drivers & Incidents and Additional Business Info, once per form and button, and Looks Good on a list that holds every intake unit; never on Quote & Coverages, whose Next leads to the agent's steps (MVR & CLUE orders reports), or later, and never the chooser's Next. Its only helpers add units (each list's add icon, the chooser's Next by `moveOn`, with "Fill the pages" or "Click Continue when the page is done" on). On GEICO the fill clicks Recalculate (once a quote), View More Payment Plans and Print Quote Proposal once nothing on Quote & Coverages is left for the agent; Next from Quote & Coverages on is the agent's.
- **Let me look before Continue** (Settings → Filling, `check-continue`, saved locally as `checkBeforeContinue`, off by default; usable while Click Continue when the page is done is on) sends `hold: true` with every fill. A page the kit would continue is held instead (`report.held = 'check'`): the panel reads the answers back (`checkAnswers`) and the dock shows **Looks right, continue** (`continueSaid`). Looks right (`lookRight`) reads the top frame's `receipt()` and fills again with it as `confirmed` (never overwriting); the kit clicks Continue only if the page's receipt still equals it after the fill and the wait before Continue, and holds again with `held: 'changed'` otherwise. With the switch on, an item settled since the fill also gets Looks right instead of Fill again and continue, and an automatic follow-up fill that is held shows its report. `receipt()` is a 53-bit fingerprint (cyrb53) of every question's key, label and what it shows in the top frame, as the agent sees it: collapsed fields a fill reads for its `hidden` rules aren't part of it, inside a fill or out, and neither are other steps' hidden fields (`otherStep`); no value leaves the page. Answers inside other frames aren't part of it. The switch is not one of the four filling switches in `fill_run.settings` (the server takes exactly those), and nothing about the hold is logged.
- On one-address applications, the panel checks that the visible step signature changes after continuation. A click is not proof of navigation or of a generated document. A Continue that didn't take (the step unchanged for about 6 s and the page not loading) is clicked once more, silently; when that doesn't take either, or on a carrier without the retry (`continueRetry: false`, GEICO: never clicked again, since it may still be working on the first; its step may load for up to a minute, and the agent is told after about 18 s of a quiet, unchanged page), automatic filling pauses, the report says "Continue didn't take: click it yourself.", and a `fill_error` (`continue did not take`) is logged. The dock's hint before a fill says Continue is clicked for the agent only while that setting is on and the carrier has an `advance` pattern; otherwise it says to click Next yourself.
- A fill keeps the context it started with (`fillContext`: its `run` id, tab, carrier, page, the intake and its revision, view, edit scope and the panel's switches), taken before it waits on anything. Auto-advance is refreshed when fill options are built after preparation, so a switch changed while list verification or AI retirement is pending controls that fill and its telemetry; pending AI approval continues to block Continue. A rejected fill logs its rule fingerprint and bounded switches with its redacted error even without a result event. Results that come back after the intake was replaced or corrected are dropped: nothing is remembered, logged or shown as the current intake's, a `fill_error` (`stale: intake changed during the fill`, no client data) is logged and the report says the page may hold the earlier intake's answers. The bookkeeping of a fill whose results come back after the agent moved to another tab goes to the fill's own tab (`rememberFill` writes into that tab's session), including its filled-page and continued-step markers. Its report, helper follow-ups, pending-page fills and Continue watcher never act on the tab now in front; delayed follow-ups and watchers also stop if the intake is replaced or corrected. Driver and trailer list verification checks the captured intake and revision before changing or persisting helper records. A rejected fill from an earlier intake produces the same stale warning, without pausing the current intake or showing the earlier error. Loading a PDF keeps every intake's edit keys and helper records, per intake and tab: the same PDF dropped again finds its own, other intakes' are pruned after 20 intakes or 30 days without being loaded, and Clear forgets the current intake's only (it is done once the helper records are gone too, and restoring helper records waits for a removal still under way, so the same PDF loaded right after a Clear doesn't get them back). Local edit keys and helper records also belong to the browser/extension session: a nonce in [chrome.storage.session](https://developer.chrome.com/docs/extensions/reference/api/storage#property-session) keeps panel reloads and intake switches together, while a browser restart or extension disable, reload or update expires the earlier numeric-tab records before any read or write. Unmarked legacy records expire once too. Initialization is shared under a Web Lock across panels; a failed expiry prevents access until it can be retried. Settings and usage logs are retained. A recorder already in the page is told to resume when the panel attaches, unless a fill or AI apply is under way, so a panel closed mid-fill doesn't leave it paused; one that wasn't paused reports what changed since its last poll instead of taking it as its baseline.

## When the carrier changes

A new question can become unfamiliar; a missing option or rejected answer can become a fill failure. When a known field looks renamed, or at least five questions and 40% of a page are unfamiliar, the fill reports `pageChanged`: the panel says the carrier seems to have changed the page and Continue waits. A renumbering leaves Progressive's questions found (`npm run e2e -- --fixtures --renumber` replays every layout with shifted ids); GEICO renumbers on every redraw and its rules hold no number (`npm run mock:geico` redraws with new numbers and checks that the agent's corrections stay protected); reworded text or a renamed data-model field leaves that question unfamiliar, never answered as another. Layouts record each field's `ref` (data-model name) since 0.9.9, and GEICO's name stem from kit version 69 (the kit is at 83), so a rule can move from text to `field`. Layout capture and rule-coverage reports provide evidence for review. This does not reliably detect a changed meaning under the same data-model name or every changed conditional branch.

Capture the affected scenario and its predecessor answers, classify mapping versus control versus semantic changes, then update a scrubbed fixture and expected outcome. Do not infer applicability merely from a field's presence or absence in one saved page. Use [corrections](corrections.md) for an observed failure and [new carriers](new-carrier.md) for expanded scenario support.
