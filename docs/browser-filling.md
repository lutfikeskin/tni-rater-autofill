# Browser filling and carrier page changes

Read this when changing control discovery, matching, repeated rows, helper actions, or navigation.

## Execution

The side panel ([coordinator.js](../sidepanel/panel/coordinator.js), [fill.js](../sidepanel/panel/fill.js)) builds a plan and injects [pagekit.js](../src/kit/pagekit.js) into the quote tab's frames. Progressive runs in `MAIN` world to access ExtJS; AmWINS and GEICO run in the extension's isolated world (`worldFor`), which shares the page's DOM, open shadow roots included. Pagekit is injected as one classic script without imports, built from its source under `src/kit/` ([kit.mjs](../scripts/lib/kit.mjs); [testing](testing.md)); bump its `__raterKit.version` when changing the injected API. The panel injects the kit with one `executeScript` and calls it with a second (`runKit`), so a frame that navigated in between has no kit. Every panel call is therefore optional (`globalThis.__raterKit?.fill(...)`). In a frame without the kit it answers null rather than throwing on the carrier's page, and a fill whose top frame had no kit is taken as a page that moved on. A sidepanel-safety test holds every call to this.

Pagekit is the engine every carrier shares: it handles plain HTML forms, ARIA, shadow roots (open ones, and closed ones where Chrome gives them) and slots, select2 and Google's address suggestions itself. A widget that writes its own way is a driver, asked in order by `apply` (`drivers` in pagekit): the address box with suggestions ([drivers/address.js](../src/kit/drivers/address.js)), a search-select and a select2 list ([drivers/select2.js](../src/kit/drivers/select2.js)), with the carrier's page adapter and a read-only field between them. Each says whether it `writes` a step to a control, `write`s it, and may say whether the control already holds the answer (`agrees`, read by `agreesWith`); it takes the engine's helpers rather than importing them. What only one carrier's pages do is that carrier's page adapter, `src/content/carriers/<carrier>.js`, which the panel injects before pagekit only on that carrier's tabs (the config's `pageAdapter`; `injectKit`). The panel puts them in (field-key.js, the adapter, pagekit and, on a `pressInPage` carrier, page-press.js) only where a frame lacks this build of the kit: each kit call (`runKit` in [fill.js](../sidepanel/panel/fill.js)) first reads each targeted frame's `__raterKit` version and build (`kitIn`; the build is learned from the panel's first injection), puts the kit into the frames without it (a new document, or an earlier build's after an extension reload or update), then makes the call; a frame whose document was replaced between the check and the call (its result null, its document not one checked) gets the kit and the call once more, so a call gives null in a frame without the kit, never an empty answer such as `[]` or `false` (audit 2026-11-07, FLOW-10, LIVE-03: the 211 KB kit went into every frame before every call). It registers `globalThis.__raterAdapter`, and pagekit reads it when it needs it (`adapter()`), so an adapter injected again replaces the old one. The hooks and their plain-HTML defaults are `NO_ADAPTER` in pagekit, typed as `PageAdapter` in [types.js](../types.js): Progressive's ([progressive.js](../src/content/carriers/progressive.js)) holds the ExtJS components (values, combo stores, focus and blur, question ids and rows, `fieldref`), its `?pageName=` page names and the helpers an answer on Rates makes due again (`rearm`); GEICO's ([geico.js](../src/content/carriers/geico.js)) names its `gds-*` components, step bar and spinners; AmWINS' ([amwins.js](../src/content/carriers/amwins.js)) its loading overlay and step tabs. A carrier's own elements go in its adapter's `selectors`, by role, and pagekit adds them to its own (`withAdapter`, `closestOwn`): a fix for one carrier's widget changes that carrier's file only. The two settings the panel needs before anything is in the page stay in the carrier config: the world the scripts run in (`world`) and whether page-press.js goes into the page's own world first (`pressInPage`). An adapter has two parts: `shared` is plain DOM (its selectors, page names, how its fields are named and keyed, Progressive's captions and combos), read by field-key.js, the recorder and pagekit alike; `create` returns pagekit's own hooks (Progressive's ExtJS). The recorder runs in the extension's isolated world, also on Progressive, where pagekit runs in the page's: `ensureRecorder` injects the adapter there as well, before field-key.js. A field's key (field-key.js) is what the agent's corrections are saved under, so an adapter's `keys` must give every field the key it had.

[field-key.js](../src/content/field-key.js) loads before both pagekit and the recorder, in each script's world. A Duck Creek field (Progressive) is keyed by its data-model name (`ref:<fieldref>`), so an agent edit stays with its question when Progressive renumbers; an edit saved by an older build under the question id still protects the field with that number, and while such a key is kept no answer already on a Progressive field is replaced (the number may be from before a renumbering, and the corrected question has a new one): one that differs from the intake is left and flagged for the agent. A GEICO field takes the same road (field key version 5, `dataName`): GEICO draws a question as `Id_<Name>_<render number>` and renumbers it on every redraw (a new step or unit form, an answer that reveals follow-ups, Recalculate), so it is keyed `ref:<Name>` from its name, else its id (a radio option's id adds its digit and `-shadow`, the VIN box `maskedField`), and a checkbox group's box (`checkbox-Id_<Name>_<n>-<Box>`) `ref:<Name>.<Box>` (`ref:AddFilings.MCS90`). GEICO's coverage lists (Quote & Coverages) have only an id, with a new UUID on every render and Recalculate: a vehicle's row is keyed by the coverage its id ends in and its place among that coverage's rows (`cov:COMP#2`; a vehicle above gaining or losing that row moves it), a policy-level list by its `[for]` caption without its tooltip (`cov:liability coverage`); a caption reading like a vehicle or an amount (a year, a VIN, a `$`) keeps the raw id, so no key carries a vehicle's year, make, model, VIN or premium. Other element names and ids keep their keys; a Progressive per-vehicle question row past the first gets `@<row>`. Checkboxes that share one name across rows, with the row only in their id (AmWINS' Vehicle Coverages), get `name#<row>` on every row; a plain name saved by an older build protects all of that name's rows. Anonymous controls use a versioned structural key anchored to their container and row, so repeated carrier fields do not share manual-edit protection or fill history. Labels and current values do not determine those keys.

Controls are read through open shadow roots in page order (a shadow root's controls where its host is). A custom element's closed shadow root is read too where Chrome hands it to the kit (`shadowOf` in [dom.js](../src/kit/dom.js): `chrome.dom.openOrClosedShadowRoot`, in an extension's isolated world, where GEICO's kit and every recorder run; not in the page's own world, Progressive's kit), and the recorder reads it the same way (audit 2026-11-07, ENG-14: a design system that closed its roots would hide the whole page). No carrier closes its roots today. GEICO's design-system controls are read as the page draws them. A `<gds-radio-button>` keeps its `<input type=radio>` alone in its own shadow root under a host of the same name: the pick is the host's `checked` attribute (an option picked earlier can keep its input checked), an option is clicked only when its host isn't checked, a stale input unchecked first, and the wait for the page also counts changes of the hosts' `checked` and their group's `active-index`. Its question is the `[slot=legend]` part of the nearest element holding every option host, without its `gds-tooltip`; an option's words are its host's `[slot=label]` (Pay In Full for `GEICO_PP_1Pay`); two groups with one data-model name (the two pay-plan lists) stay two questions. A `<gds-button>` keeps its words in the page and only `<slot>`s in its shadow `<button>`: a button reads as its own text, else its slotted text, else, inside a button host's shadow root, the host's (`buttonText`), and a disabled host disables it. A select2 list (its own `<select>`, hidden by select2, with select2's box after it) is answered the way the agent answers it, and marked on that box: the box opened with a left-button mousedown, the option's text typed in the list's search box (on a list taking several, the box inside the list's own), and the one result reading exactly that text clicked; a list that shows it no time or several times when it's typed is the agent's ("the list didn't show … when it was typed; pick it yourself"), and on a list taking several a pick the answer doesn't name is taken off first with its ×. GEICO takes only select2's own pick, never a change set on the hidden `<select>` (FL live run 6, 2026-10-21: the commodity set there showed, but GEICO took none and never asked for the cargo limit; the business description set so was refused at Next). A `search-select` rule (AmWINS' classification, whose results come from its server) types its `search` words instead and picks the one result reading its value, else the one result having its words (a check item, as a choice's fallback below); a pick agrees with its answer by the same rule: it reads the answer, or has its words while no option of its `<select>` reads exactly so (options the `<select>` kept from an earlier search are no rivals: which result was the only one was the write's to judge). A list taking several choices (the cargo commodities: a `<select multiple>`) gets exactly the answer's options, named by their texts joined by "; " (as it reads back), each of which must be offered and enabled (else "no option matches" and nothing is picked; an option whose own text has "; " in it is one pick), is failed when the page doesn't keep the picks, and agrees with the same picks in any order (W43-23); an AI suggestion the agent approves there is one option; a hidden, disabled or empty-value stand-in option (each coverage list starts with one repeating its choice) gives way to a real option reading the same. The street box, a search input with its own suggestion list (`aria-autocomplete=list`, `aria-controls`, not select2's filter box), is a question; other search boxes aren't. An `address-suggest` answer types the whole address and picks the first new suggestion for it: Google's (`.pac-item`) with its house number, any other with the same leading house number and, when both show one, the same ZIP after the state (another town's same street is not it). GEICO's suggestions are `<gds-dropdown-list-item type="address">` items in its address wrapper's shadow root, read as list items, not options (GEICO's script; the open list was never captured). Suggestions shown but none for the address leave the street (`fallback`) for the agent: "none of the page's address suggestions has the intake's house number and ZIP". With `checkNumber` (GEICO's street), what the fill left in the box stays the agent's on later fills while the box still holds it ("no address suggestion was picked for it"), and a street the page filled itself agrees only with the intake's house number. An `aria-label` written as markup (tags, `**`) is read as its text, and a field without a label, or with one of no letters (an amount box showing only `$`), is named by its humanized data-model name ("give year"), never its render number. GEICO's spinners (`#page-load`, `#extendedWaiting`) count as the page being busy. A text box showing only its input mask (`MM/DD/YYYY`, `__/__/____`, a VIN's underscores: `MASK_ONLY`) is empty: it is filled, and the mask is never reported as the page's own answer (FL live run, 2026-10-21: the owner's date of birth and the VIN were left as differing from the intake). A list with one distinct option (GEICO's collision row lists "Not Included" twice until its comprehensive is chosen) is still loading: its answer waits up to six seconds for the rest (FL live run 2, 2026-10-21: two collision rows failed before GEICO drew their deductibles). A rule's `waitFor` (a data-model name; plan.js resolves it per unit) holds its answer while that question is on the page unanswered, or not drawn yet, for up to eight seconds, a round every 0.4 s: GEICO's vehicle form, with a VIN, waits for the decoded year, since the decode redraws the form and clears the type, distance and personal use given before it (FL live run 2: the Cascadia's Tractor was cleared three times; FL live run 3, 2026-10-21: the year is drawn only by the decode, and the type given before it was cleared). Once the question it waited for is answered, the fill waits for the page to be quiet for 0.8 s before giving the held answers (the decode redraws the type list a moment after the year). One still waiting when the fill's rounds run out is reported failed ("the page was still working on this question"). A question waited for the whole eight seconds isn't waited for again: one on the page, in that document; one never drawn, on that form (a VIN GEICO doesn't decode leaves the year empty for the agent). With nothing more to do, a fill that filled something with such a question's step on the page looks once more: it waits for the page to be quiet (0.8 s, up to eight seconds) and reads it again, so an answer a late redraw cleared is given again (`retryOnce`). The recorder reads the same way: shadow-root controls in page order, a radio's pick from its host once the host shows it, a `<gds-button>` click by its slotted words, and the street box.

The fill loop collects controls, assigns rules, applies answers, waits for the page, rereads values, judges the questions above its cursor (below), and rescans. Server-backed pages generally fill one answer per round; a carrier with `batch: true` fills a visible round before settling. Enable batching only with evidence about that carrier's behavior. Answers given one at a time go down the page, in the order its controls are read, whatever order the rules are written in, so what an answer draws under its question is answered before the questions further down. In rule order a fill went up and down the page (GEICO mock, Business & Owner Info: the business name, 14th of 16, first, then the owner's name at the top). A batch round keeps the rules' order: its answers land together, and AmWINS' driver rules give the names and license number before gender, marital status and the license year, which sit between them on the page.

### Judged at the cursor

The carrier page is answered top to bottom: what is above decides what appears below (the maintainer, 2026-10-28). The fill answers and judges in that order. Each round's cursor is the first question in page order the fill still has to act on: an answer to give, or one waiting for the page (`waitFor`, an answer the page didn't keep, a prerequisite to give again). Questions above the cursor are judged as before: needs you, unfamiliar, failed, a check, a kept answer that differs, a row no unit matched, an answer the page marks invalid. Questions below it are provisional. They get no item, no mark and no blocker, and the panel is sent nothing for them, until the cursor reaches them. When the fill has nothing left to act on, the round judges everything left on the page from the same read, and `reconcile` (below) then runs on the fill's final read as the safety net.

- One answer at a time stops at the cursor. An answer the page didn't keep, a question waiting for the page (`waitFor`) and a `needs` prerequisite still to give again all hold the cursor where they are, and nothing below them is answered or judged until they are settled. Before this, on a page that isn't ExtJS (GEICO), the loop went on past them and answered and judged further down.
- Where the page isn't ExtJS and fills one answer at a time (GEICO), an answer's redraw may land after the page went quiet. GEICO took Property Damage and UMPD off the page a moment after the CSL limit. The next round therefore judges nothing below the last answer until it has given its own answer further down and the page has settled again (`lagBound`). Then what waited is judged from the same read, if its field is still in the page (`isConnected`): one an answer above took away is never an item. A choice that found no option there is tried again in a later round instead of failing against options the page may still redraw (UM against the split limits). Live GEICO run, 2026-10-28 (usage session 75b6, 20:23 UTC): round by round, Property Damage and UMPD were made needs-you items before the $1,000,000 CSL above them removed them, and UM failed against the split limits; now no round makes them items, and `reconcile` has nothing to drop.
- Page order is the kit's control order (through shadow roots, as read). Progressive's Rates rows are judged in that order within the group of units shown. A unit whose rows aren't shown isn't read, so it isn't judged until its group is (`pager`), and the pager turns only when the round had nothing left to act on. A section opened by a helper ("+", a card's chevron) is read once its opener is pressed, and the cursor moves into it. A batch (AmWINS, `batch: true`) has its cursor at the end of the visible batch: everything it shows is judged each round, as before.
- Helpers keep their prerequisites (`after`, `afterActions`, `needs`). A `whenClear` helper also waits while any question is still below the cursor, unjudged (`provisionalLeft` in `leftForAgent`). A fill whose rounds run out with questions below its cursor stops with the round-limit halt, so none is taken for nothing left.
- Nothing more is read or waited for: each round's judgments use its own read, and a second pass over what waited reuses it. On `npm run mock:geico` the filling time went from 65.0 s to 62.7 s over 33 fills (166 to 164 rounds; the first vehicle's form, which waits for the VIN decode, 6.9 s to 4.5 s).
- The panel shows what the fill judges while it runs. Each round the kit makes one snapshot of its items, each with its place on the page as the round read it (`streamItems`). `progress` returns it only when the panel doesn't have that round's (`items@<frame>`), with each answer's place (`order`). The live list (`LiveView` in `live-view.jsx`, `liveEntries`) shows the answers and the items in the page's order, frame by frame. The review list after the fill is in page order too (`order`, from the final read).

On a one-address application the kit reads the step on screen (`stepKey`, exported as `step`): AmWINS' visible headings; on a page with a step progress bar (GEICO's `<gds-progress-bar>` parts), the one part under way (value between 0 and 100), and only while `document.title` names it too. The title and the form were seen to be one step's while the bar was another's mid-redraw (FL capture 007): then no step is read, and a fill whose plan has rules kept to steps does nothing there. Checked at every round, it halts ("The step on screen could not be read (the progress bar and the page title disagree): fill again once the page settles.") and reads nothing for its report: no unfamiliar or required items, marks, `pageChanged` or Continue, and `report.stepKey` is `''`. Unlike other halts it doesn't pause automatic filling (`report.stepUnread`), and the panel's report doesn't say it does: an automatic fill that comes back so is tried once more about 1.5 s later (with automatic follow-ups on, while the tab is still on that page and intake), and not again until a fill reads a step; a fill the agent asked for isn't retried. Luna is asked nothing about it. A fill that began on a step it read and then reads none ends as on the agent's Next (below). The recorder reads the step the same way. On a page with a progress bar a fill ends when the step on screen changes (the agent's Next): nothing more is given or clicked, nothing on the new step is marked or reported, Continue is not clicked, and the report is filed under the step the fill started on (`report.stepKey`); the new step gets a fill of its own.

A carrier rule finds its question by what it is, never by a remembered question id: Progressive renumbered every question on 2026-10-07, and ids kept from before put answers into other questions (Business Name got the trucker type). Its field's data-model name (`field`: Duck Creek's `fieldref`, such as `RiskInput.VIN`, or GEICO's name stem, such as `GiveYear`, on any page) comes first, and the rule's wording (`ask`/`label`) is then a check: a field found by name whose question reads differently is answered and flagged for the agent (`reworded`), never one with no caption or label of its own, whose "label" is only its name (`nameOnly`: Progressive's TX PIP limit, taken for reworded, held the Rates helpers, live recording, 2026-10-23); one we leave as the page has it (`ignore`, `verifyOnly`, which can depend on the unit: GEICO's year, make and model when the intake has the VIN GEICO decodes) becomes a check item. A name is looked for (and keeps text rules off its field) on any page except where the rule is fenced off: Progressive's trailer pages carry the vehicle's names, so the vehicle's rules have `notPages` (the trailer pages) and the trailer's `pageOnly` (Add Trailer, or Rates for its row). On a one-address application whose steps share names (GEICO's `GiveFirstName` is the owner on Business & Owner Info and a driver on Drivers & Incidents), a rule names its steps (`steps`, against the step read from the page), and a rule for one form of a step names a question only that form asks (`whenShown` / `unlessShown`: `{ field, label?, unit? }`, a field with that data-model name on the page and, with `label`, a question matching it: GEICO's vehicle, trailer and driver forms); a rule that isn't live there neither answers nor claims a field, and a label rule kept to steps is a known question, as one kept to pages is. A data-model name missing from the page while its wording is there is a probable rename (`renamed`): that field is left with the agent. Otherwise the question's text on the rule's page (`ask` exact, or `label`), never a field another rule knows by name, after an anchor question when the text repeats (`askAfter`: the business and the owner's "City"; a field found by name needs no anchor), of a given field kind when two kinds share it (`control`; a choice or yes/no answer never goes into a text box), or the list offering a given answer (`withOption`). A step that only has an id finds nothing, and a known question that isn't found stays with the agent rather than falling back to a looser label rule. Each answer records what found its field (`how`). Selectors and known options come next, then label fallbacks. Rows of one question share an id on the page, which is compared with the page itself only; the active vehicle index alone does not prove which visible column belongs to it. A label fallback never takes one of several rows of a question, or a question the plan answers per vehicle; ambiguous rows (two vehicles that read the same) stay with the agent. A repeated selector rule can name a row's witness instead (`witness: { selector, path }`, resolved per unit by the plan): among the controls its selector finds, the step takes the one whose row (the nearest ancestor holding a control matching the witness selector, which must be the only one there) shows the unit's value, letters and digits compared; AmWINS' vehicle rows are each found by their VIN this way, since Import Valid Records draws them in its own order. No row showing the unit's value (the import hasn't landed or rejected its VIN; the intake has no VIN for it), or two rows showing it, gives the unit no row: its answers stay the agent's, with one note naming the unit ("the row for vehicle 2 (its VIN) wasn't found") and never its VIN, and the rows the rule chooses among are known questions, never unfamiliar ones. A row showing a value no intake unit has (a vehicle on the quote the intake doesn't list) is never answered or changed: it is one check item named by its place ("Vehicle row 4 on the page"), never its value, and Continue waits for the agent to remove the row or explicitly dismiss that check to keep it. Its opaque acknowledgement key contains no VIN, survives redraws, row reordering and unrelated application steps without visible witness rows within the current document, and does not carry over to a different VIN or a new document. Removing an extra identity while witness rows are visible, then re-adding it, requires new confirmation. Duplicate extra rows each require confirmation bound to that DOM row; changing their count or redrawing those ambiguous rows requires new confirmation. Reacquire controls after redraws and verify the retained value. A list that is still empty when its answer comes (one filled in by another answer, such as Progressive's cargo commodities after their category) gets a few seconds to load before nothing matches. Retries are bounded; do not bypass acceptance checks to improve completion counts.

A choice is the option reading as the answer, then as one of its aliases (`choiceAliases`), then the one option beginning with their words, then the one having them, whole words only ("No" doesn't begin "None" or "Not sure", and "Van" isn't in "Caravan"). An option found by one of those two fallbacks is still the answer given, but the engine isn't sure of it: the report lists it as a check item (amber on the page, never green) naming the option and how it matched (`matched`: `prefix` or `contains`), on the fill that chose it and on each later fill that finds the page holding it (the maintainer, 2026-11-07). A yes/no answer takes no fallback: only Yes or No (Y, true / N, false as an option's value) or the step's own aliases, so an option worded otherwise (Progressive's Refrigeration Breakdown "Yes, match Motor Truck Cargo limits") is named in its rule's `choiceAliases` for that answer, and a list without either is no match. A rule with `matchStart` takes only the first kinds, the answer before each alias in turn, so an option that only mentions the answer further on is never it: Progressive's business type lists read "<name> <description>", and "Auto Hauler (For Hire Trucking)" is not For Hire Trucking. An option beginning with the answer there is the rule's own declared match, not a fallback, so it is no check item: Progressive's payment method reads "Automatic payments from checking account" followed by its tagline. A type-ahead list is narrowed first by the word the rule's `search` gives, as the agent types it: a select2 list (`search-select`: AmWINS' classification) or an ExtJS combo (its `doQuery`: Progressive's LA business description, "Trucking"), and the answer is picked among those results only; none matching is a miss, which a rule with `unofferedNote` leaves to the agent with that note. Where the word goes into a box of its own and a Search shows the results (Progressive's Business Type Selection popup in KY), the box is a rule (`unlessShown` the result list, so it isn't typed where the list already shows) and its Search a helper kept inside the popup (`within`), never the page's box or Search behind it ([Intake and rules](intake-and-rules.md), TNI 2026-10-28).

### DOM events, not the debugger

The kit acts on a carrier page the way a script can: it writes values through the control's own setter, dispatches `input`, `change` and key events, and clicks with `click()` or from the page's own world ([page-press.js](../src/content/page-press.js)). It doesn't use the Chrome DevTools Protocol (`chrome.debugger`: `Input.dispatchMouseEvent`, `Input.insertText`, network idle, a DOM that pierces shadow roots).

**Why not the protocol.**
- The `debugger` permission can't be optional. Chrome warns when it is installed or added, and disables the extension until the agent accepts.
- Chrome shows "is debugging this browser" on every tab while the debugger is attached. The developer recording turned it down for screenshots too ([Developer recording](developer-recording.md), its screenshot choice).
- Every licensed agent would have to accept the warning, and the store review weighs the permission.
- The protocol's events are trusted, but that is all it would give the fill. The DOM-event fill already works on the three carriers.

**The cost: the page sees script events, not the agent's.** Each gap has its own fix:
- **React 18 clicks:** pressed from inside a dispatch in the page's own world (page-press.js, W43-44).
- **select2:** a `MouseEvent` with `button: 0` ([select2.js](../src/kit/drivers/select2.js)).
- **Google's address suggestions:** a `keyCode` set on the key events ([address.js](../src/kit/drivers/address.js)).
- **GEICO's Print Quote Proposal:** clicked by the kit (`kitClick` in [geico.js](../src/carriers/geico.js)), because the page-world press never opened the proposal. Why is not known.
- **Not covered:** a field that rejects one-write input (an input mask, a read-only date picker). That field is left for the agent.

**When to look again.** Look again only when every agent's Chrome installs the extension by policy (a managed build, so no agent has to accept the warning), or when a carrier needs trusted input that page events can't give. Until then, a new gap gets a fix in the carrier's page adapter or a driver, as above.

## Review and navigation

- Unknown fields are marked; supported fields can still fill. An unfamiliar question that went away during the fill (hidden by an answer) is not reported. Missing data, failures, differing retained values, confirmations, and blocked helpers contribute to the review report. A field drawn without a caption is named there after its rule. A helper that opens the next page (the vehicle tile) leaves that page's questions to its own fill; none is reported as the earlier page's.
- The kit marks the fields it handled on the page (`mark`, `COLORS`; the title starts "Rater Autofill:"): an intake answer, or one worked out from it, solid green; a TNI standard (a plan step with `standard`, rule `source: 'standard'`) solid blue, so the agent can tell assumptions from intake facts; an agent's own default in place of one (`source: 'agent-default'`, [agents' own defaults](agent-defaults-spec.md)) solid teal; one left for the agent (missing data, a check item, including a standard to confirm in review mode, an unfamiliar or required question) dashed amber; one it couldn't fill dashed red; an AI answer solid purple; a choice the agent picked in the panel (`answer` with `by: 'agent'`) solid slate, so it isn't taken for an intake answer. A follow-up fill keeps the marks of answers already in (`keepMarks`); `clear` removes them all. The page list's key (the **i** in its title, `key-btn`: **Marks on the rater page**) shows the same colors (`--mark-*` in [sidepanel.css](../sidepanel/sidepanel.css), which a pagekit test keeps equal to `COLORS`).
- Unfamiliar fields block advance when required or unanswered. Optional prefilled unknowns do not always block; explicit optional/ignored rules and agent dismissals also affect this behavior.
- Review-mode standard choices require confirmation even when the carrier preselected a different answer. The retained value is preserved; Continue waits until the agent acknowledges that field.
- The registered-name check (`businessNames`, Progressive's USDOT lookup): while the page shows a registered business name that isn't the intake's, a step with `businessNames` is not answered; it is the agent's (`noData`, `reviewOnly`, "The DOT lookup business name differs from the intake"). When that name shows only after such an answer went in (Progressive draws it right after "belongs to the business" Yes), the answer stays on the page but moves from `filled` to `noData` with the same note and is marked amber, so Continue waits. The kit checks this each round, at the end of the fill and again after the wait before Continue (`identityAfterAnswer`), where a move adds a `needs you:` blocker and Continue is not clicked. A field the agent edited is theirs and is left alone. ## Only what is on the page

The review list never invents a value and never shows a question or a value the rater page doesn't have: in its review state it shows only what is on the page at that moment (the maintainer, 2026-10-28). An answer can take questions off the page or redraw them after the fill read them (GEICO live run, 2026-10-28, TX: a $1,000,000 CSL liability limit removed Property Damage Liability and UMPD and redrew UM's limits as CSL; the report kept both as "Needs your answer… On the page now: $25,000" on a page without them, they held Recalculate until the agent marked them done, and UM, tried against the split limits shown before the redraw, failed). Judged at the cursor (above), the fill no longer makes those items at all. What follows is the safety net for whatever still changes after a question was judged (a question above the cursor that an answer below it takes away, a redraw later than the next answer's wait, the page after the fill). One mechanism, the same for every carrier:

- As a fill ends on its page (`reconcile` in [pagekit.js](../src/kit/pagekit.js)), its report is made to agree with the page from the read the end of the fill already makes (no read or wait of its own; that read now also serves the marks, which read the page a second time before): an item left for the agent (unfamiliar, failed, needs you, required, check, a kept answer that differs) whose field is gone is dropped, so it is no blocker and the panel never lists it; every other one takes what its field shows and offers now (`current`, `options`), and its key and label where its rule now finds another row. Kept off screen (`offPage`): a question read while another group of units was shown (`pager`, 'group'), one in a coverage section the page closes (a carrier's `sections`: Progressive's cargo, GL and trailer interchange, 'section'), one whose field is in the page but not shown or open (a collapsed card, such as GEICO's cargo card after Recalculate; a disabled field: 'hidden', from the same read's fields it passed over), and a failed answer whose field the page took away on it, a summary in its place (`vanished`, 'answer'): these say nothing of what the page shows. A row the intake doesn't have (`extra-row:`) stays while the page shows it. The answers listed (filled, and kept as the page had them) are held to it the same way: each stays in the report, for what the fill did (the usage log, the panel's bookkeeping), with what its field shows now (`now`: the panel shows that, never the value the fill put in), `changed` where that is no longer the fill's answer as the fill judges it ('you' for a field the agent took over, else 'page'), and `gone` where its field has left the page (GEICO's chooser answer once the vehicle form replaces it); the panel lists no row for a gone answer and shows a changed one as the page's or the agent's, not counted as the fill's. The report's `reconcile` says the time it took, the reads since the rounds ended (1), the items dropped, the answers gone and the choices given again; `npm run mock:geico` prints them, and each fill's answers gone (30 fills, 10.1 ms in all, 1.2 ms at most, one read each, one answer gone; the filling time unchanged).
- During the fill too, only an item whose question is on the page holds a `whenClear` helper (`leftForAgent`, `liveOn`): GEICO's Recalculate no longer waits on a question an answer took away.
- A choice that failed against options the page has redrawn since (its `options` at the failure differ from the field's now) is given once more against the ones the page shows, in the next round, as any answer (`retryRedrawn`, once a fill; never after a halt or the agent's own button). With UM's CSL limits drawn, UM takes `$100,000 Combined Single Limit` (Texas' alias).
- The panel shows only what the kit read as the page's: "On the page now", a failed item's options and the row's choices come from the fill's reconciled report or from its own reading since, never from what an earlier round read. Its reading (`checkItems`) is one message for all the items of the report shown (the kit's `present(items, hidden, steps)`: one read of each frame, `describe` for each item found, so a box's typed text never leaves the page as `current`, with `shown` and `agrees` for the answers' rows as `readBack` gives them; `shared` where rows of one question share the key and the label doesn't tell which; `hidden` for one in the page but not shown, which stays and says nothing). It runs when the recorder says the page in front changed (answers, questions drawn or gone, a step or page shown; 300 ms after the last), when **Show on page** doesn't find the field, and when the agent opens This page once it's filled. An item whose field is gone and isn't `offPage` leaves the list (hidden, `gone`; back if the page draws it again) and holds nothing: the count, the dock and Continue go without it, with no Mark done needed. A settled item (answered, picked, marked done) is left as it is, Mark done's Undo included. The answers' rows are read in the same message: one whose field is gone has no row (back if drawn again); one whose field shows something else shows that, tagged **Changed on the page** where the kit wouldn't call it the fill's answer. A page that can't be read (navigating, no kit) changes nothing.
- A kept report made again on reopen (`restoreReports`, `liveFrames`) is of the page as it is now: the page in front's items are read in one message before it shows, so a question or answer gone since never shows again and each answer shows the page's value; another page's or step's say nothing of their page until it is in front and read.

## When the carrier changes

A new question can become unfamiliar; a missing option or rejected answer can become a fill failure. When a known field looks renamed, or at least five questions and 40% of a page are unfamiliar, the fill reports `pageChanged`: the panel says the carrier seems to have changed the page and Continue waits. A renumbering leaves Progressive's questions found (`npm run e2e -- --fixtures --renumber` replays every layout with shifted ids); GEICO renumbers on every redraw and its rules hold no number (`npm run mock:geico` redraws with new numbers and checks that the agent's corrections stay protected); reworded text or a renamed data-model field leaves that question unfamiliar, never answered as another. Layouts record each field's `ref` (data-model name) since 0.9.9, and GEICO's name stem from kit version 69 (the kit is at 94), so a rule can move from text to `field`. Layout capture and rule-coverage reports provide evidence for review. This does not reliably detect a changed meaning under the same data-model name or every changed conditional branch.

Capture the affected scenario and its predecessor answers, classify mapping versus control versus semantic changes, then update a scrubbed fixture and expected outcome. Do not infer applicability merely from a field's presence or absence in one saved page. Use [corrections](corrections.md) for an observed failure and [new carriers](new-carrier.md) for expanded scenario support.
