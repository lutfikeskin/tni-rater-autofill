# Browser filling and carrier page changes

Read this when changing control discovery, matching, repeated rows, helper actions, or navigation.

## Execution

[sidepanel.js](../sidepanel/sidepanel.js) builds a plan and injects [pagekit.js](../src/content/pagekit.js) into the quote tab's frames. Progressive runs in `MAIN` world to access ExtJS. Pagekit is a classic script without imports; bump its `__raterKit.version` when changing the injected API.

[field-key.js](../src/content/field-key.js) loads before both pagekit and the recorder, in each script's world. A Duck Creek field (Progressive) is keyed by its data-model name (`ref:<fieldref>`), so an agent edit stays with its question when Progressive renumbers; an edit saved by an older build under the question id still protects the field with that number, and while such a key is kept no answer already on a Progressive field is replaced (the number may be from before a renumbering, and the corrected question has a new one): one that differs from the intake is left and flagged for the agent. Element names and ids keep their keys; a Progressive per-vehicle question row past the first gets `@<row>`. Checkboxes that share one name across rows, with the row only in their id (AmWINS' Vehicle Coverages), get `name#<row>` on every row; a plain name saved by an older build protects all of that name's rows. Anonymous controls use a versioned structural key anchored to their container and row, so repeated carrier fields do not share manual-edit protection or fill history. Labels and current values do not determine those keys.

The fill loop collects controls, assigns rules, applies answers, waits for the page, rereads values, and rescans. Server-backed pages generally fill one answer per round; a carrier with `batch: true` fills a visible round before settling. Enable batching only with evidence about that carrier's behavior.

A carrier rule finds its question by what it is, never by a remembered question id: Progressive renumbered every question on 2026-10-07, and ids kept from before put answers into other questions (Business Name got the trucker type). Its field's data-model name (`field`: Duck Creek's `fieldref`, such as `RiskInput.VIN`, on any page) comes first, and the rule's wording (`ask`/`label`) is then a check: a field found by name whose question reads differently is answered and flagged for the agent (`reworded`); one we leave as the page has it (`ignore`, `verifyOnly`) becomes a check item. A name is looked for (and keeps text rules off its field) on any page except where the rule is fenced off: Progressive's trailer pages carry the vehicle's names, so the vehicle's rules have `notPages` (the trailer pages) and the trailer's `pageOnly` (Add Trailer, or Rates for its row). A data-model name missing from the page while its wording is there is a probable rename (`renamed`): that field is left with the agent. Otherwise the question's text on the rule's page (`ask` exact, or `label`), never a field another rule knows by name, after an anchor question when the text repeats (`askAfter`: the business and the owner's "City"; a field found by name needs no anchor), of a given field kind when two kinds share it (`control`; a choice or yes/no answer never goes into a text box), or the list offering a given answer (`withOption`). A step that only has an id finds nothing, and a known question that isn't found stays with the agent rather than falling back to a looser label rule. Each answer records what found its field (`how`). Selectors and known options come next, then label fallbacks. Rows of one question share an id on the page, which is compared with the page itself only; the active vehicle index alone does not prove which visible column belongs to it. A label fallback never takes one of several rows of a question, or a question the plan answers per vehicle; ambiguous rows (two vehicles that read the same) stay with the agent. A repeated selector rule can name a row's witness instead (`witness: { selector, path }`, resolved per unit by the plan): among the controls its selector finds, the step takes the one whose row (the nearest ancestor holding a control matching the witness selector, which must be the only one there) shows the unit's value, letters and digits compared; AmWINS' vehicle rows are each found by their VIN this way, since Import Valid Records draws them in its own order. No row showing the unit's value (the import hasn't landed or rejected its VIN; the intake has no VIN for it), or two rows showing it, gives the unit no row: its answers stay the agent's, with one note naming the unit ("the row for vehicle 2 (its VIN) wasn't found") and never its VIN, and the rows the rule chooses among are known questions, never unfamiliar ones. A row showing a value no intake unit has (a vehicle on the quote the intake doesn't list) is never answered or changed: it is one check item named by its place ("Vehicle row 4 on the page"), never its value, and Continue waits for the agent to remove the row or explicitly dismiss that check to keep it. Its opaque acknowledgement key contains no VIN, survives redraws, row reordering and unrelated application steps without visible witness rows within the current document, and does not carry over to a different VIN or a new document. Removing an extra identity while witness rows are visible, then re-adding it, requires new confirmation. Duplicate extra rows each require confirmation bound to that DOM row; changing their count or redrawing those ambiguous rows requires new confirmation. Reacquire controls after redraws and verify the retained value. A list that is still empty when its answer comes (one filled in by another answer, such as Progressive's cargo commodities after their category) gets a few seconds to load before nothing matches. Retries are bounded; do not bypass acceptance checks to improve completion counts.

## Review and navigation

- Unknown fields are marked; supported fields can still fill. An unfamiliar question that went away during the fill (hidden by an answer) is not reported. Missing data, failures, differing retained values, confirmations, and blocked helpers contribute to the review report. A field drawn without a caption is named there after its rule. A helper that opens the next page (the vehicle tile) leaves that page's questions to its own fill; none is reported as the earlier page's.
- The kit marks the fields it handled on the page (`mark`, `COLORS`; the title starts "Rater Autofill:"): an intake answer, or one worked out from it, solid green; a TNI standard (a plan step with `standard`, rule `source: 'standard'`) solid blue, so the agent can tell assumptions from intake facts; one left for the agent (missing data, a check item, including a standard to confirm in review mode, an unfamiliar or required question) dashed amber; one it couldn't fill dashed red; an AI answer solid purple. A follow-up fill keeps the marks of answers already in (`keepMarks`); `clear` removes them all. Step 3's key shows the same colors (`--mark-*` in [sidepanel.css](../sidepanel/sidepanel.css), which a pagekit test keeps equal to `COLORS`).
- Unfamiliar fields block advance when required or unanswered. Optional prefilled unknowns do not always block; explicit optional/ignored rules and agent dismissals also affect this behavior.
- Review-mode standard choices require confirmation even when the carrier preselected a different answer. The retained value is preserved; Continue waits until the agent acknowledges that field.
- The registered-name check (`businessNames`, Progressive's USDOT lookup): while the page shows a registered business name that isn't the intake's, a step with `businessNames` is not answered; it is the agent's (`noData`, `reviewOnly`, "The DOT lookup business name differs from the intake"). When that name shows only after such an answer went in (Progressive draws it right after "belongs to the business" Yes), the answer stays on the page but moves from `filled` to `noData` with the same note and is marked amber, so Continue waits. The kit checks this each round, at the end of the fill and again after the wait before Continue (`identityAfterAnswer`), where a move adds a `needs you:` blocker and Continue is not clicked. A field the agent edited is theirs and is left alone. An answer the page marks invalid is normally given again, at most twice; one the identity check left to the agent is not, nor a `keepChoice` answer this fill didn't give. Those are flagged failed and left as they are.
- Agent edits are protected; an edit during filling interrupts the run. Keep that protection across retries and AI responses. The recorder is paused while the kit puts answers in (a fill, an AI apply), so the kit's own edit guard (`guardEdits`: a trusted input/change within 2 s of a trusted gesture on that same control: the control, a radio of its group, its label (`label[for]` or a wrapping label; for a radio, the label of any radio in its group), its ExtJS trigger wrap, a detached dropdown option resolved to its ARIA owner or the control focused when the gesture occurred, or an element holding no other control; an agent click elsewhere just before the kit's own radio or checkbox click is not an edit) catches the edit, protects its key and halts; the guard stays on through the wait before Continue, so an edit there stops the Continue and the halt reason is a blocker (`advanced` is recorded only once the click went out). The same guard runs during an AI apply (`answer()`): the edited question keeps the agent's answer and the answers still to come are refused with that reason (each item of an edited question carries `protected: true`, and an edited question that was not among the answers gets a protected item of its own; the panel adds those keys to the agent's protected keys, as after a fill). On a page with several frames the panel keeps guards active in every frame for the full AI apply and sends one answer at a time to its originating frame. It checks all frames between answers: an edit in a frame whose answers are still to come or have already finished protects that question and refuses every remaining answer. Every dispatch requires its original guard session; a replaced document or changed intake context stops the remaining answers. Trusted edits caught before the apply ends are saved under the original intake fingerprint, tab, and vehicle/driver/page scope even if the panel has switched away; returning to that quote or reloading the panel restores those keys without storing answer text. Replacing the intake retains these separately scoped records; explicit Clear erases the current intake's records and cancels its late guard writes, while another intake's in-flight edits remain protected. These records share the browser/extension session boundary described below. The guards are released when the apply finishes, including transport failures. When the pause ends, the recorder reports the agent's own edits made meanwhile as theirs (a trusted value still on its control, a question the fill revealed included) before taking the new baseline; while paused it counts a trusted input/change only within 2 s of a trusted gesture on that control (the same targeting as `guardEdits`, so the gesture of an agent edit that started a follow-up fill does not claim the fill's click on another radio), since the kit's own click on a radio or checkbox fires trusted input/change too; the extension's own answers and the questions they revealed are not reported (the panel logged the fill, and the fill answered them).
- Trusted native input/change events identify the exact control the agent answered, including a dropdown selection made after a long delay. A prefilled or page-generated value alone does not resolve missing intake data; explicit review notes still require confirmation.
- Helper actions use prerequisites and quote/entity scope (vehicle, trailer, driver). A click alone is not a result: a helper with `verify` is done only once its result shows (`premium`, `gone`, `cargoClosed`; `revealed`: a question appeared or an answer changed since a snapshot taken as the button was clicked, which is how Progressive's Lookup VIN and Verify USDOT and AmWINS' Import Valid Records count, since the page redrawn with the same questions and answers is no result; `{ appears: '<selector>' }`: more of that selector than before the click), else it is unclicked and reported as not verified. A `revealed` helper with `shownBy` (Progressive's Lookup VIN: the decoded year, make and model, all answered; Verify USDOT: any of the USDOT record's questions, including the no-record branch's 60-day question) whose result already shows for the unit's value on the page (the agent ran it before Fill; the value is the intake's and this fill didn't type it) is done without a click (reported with `alreadyShown`, no follow-up fill), even when the lookup button is absent or disabled; its prerequisites still hold. A click that redraws that result unchanged counts too. A `revealed` or `appears` helper is tried twice more in the same fill; then it stays blocked and the agent is told to do it by hand. A helper without `verify` counts on click. A button the carrier refuses while a required question is empty (`waitRequired`: Progressive's bill plan, Recalculate, Print) waits for it and names it. A helper the agent does by hand (`missing`: its needs-you item) can hold later helpers (`heldBy`) until it is settled: its button back on the page (`resolvedBy`, the Add NTL link after NTL was removed) or a page the agent has been to since (`settledByPages`: Progressive's General Liability item, settled once the agent has been to the bill plan, which they open after adding GL; until then Recalculate and Print wait, named "General liability resolved"). A helper the fill didn't click is reported in `blocked` with what it waits for: `why` in ids and paths (the usage log's `button:` blockers) and `waits` (the same, by kind: fields, helpers, pages). The panel doesn't list them: a question one waits on is already a needs-you item, and the fill clicks the others in turn. A helper that waited only for answers the page now shows, and whose button the page took away before it was clicked, is done without a click, as one already shown is (`alreadyShown`: "done by the page itself"), so it isn't left waiting and a helper that follows it isn't held (SC 2026-10-19: Progressive looked a second vehicle's VIN up by itself once it was typed). Progressive's trailers follow the vehicles: Add Trailer once every vehicle's lookup is done, the trailer tile, then Add Trailer. A driver or trailer counts as entered once Progressive took its page (its list comes back from Add Driver or Add Trailer); opening it, or answers filled there alone, don't count. On the vehicle list a vehicle counts as added (its lookup and Add Vehicle done, also when the agent ran the lookup) once the agent has come back to the list from that vehicle's pages (`vehicleReturned`, `unitArrival`) and the list shows its VIN, so Add Vehicle is never clicked for it again. The VIN alone isn't enough: the list also shows the vehicles the USDOT lookup found, which are on the quote only once added. A VIN not shown proves nothing. A trailer is checked against the list itself, which shows each unit on the quote with its VIN: its VIN there means entered, and a list showing the vehicles' VINs but not the trailer's means not (back by Back or the top menu). On the driver list a driver shown by first and last name on one line (one driver, not two names mixed) is entered (also when the panel was closed while the agent finished the driver's page); a name not shown proves nothing, and neither does one shown that another intake driver's name holds (two drivers with the same name). When Add Trailer can't be found, or Add Driver or Add Trailer was opened but its unit never entered (`doneWhen`, `unfinished`), the agent is told, so Vehicle Summary's Continue never leaves an intake trailer out. A helper's "do it yourself" note is not shown once what it adds is in. The buttons clicked and the units entered are kept per intake and quote tab, so a panel closed or reloaded mid-quote doesn't add a vehicle, driver or trailer again. Loading another intake and then returning to the original fingerprint restores those helper markers too. A helper whose button shows only once the page took an answer can name that answer (`nudge`: Progressive's Done with this coverage after the cargo commodity): with everything else ready and no button, the answer is picked again, once. A helper that answers many questions at once (`skipIfProtected`: AmWINS' Default all answers to No) is not clicked, and not counted as clicked, while an answer the agent gave is on the page: it would reset that answer, and the per-question rules fill the other questions one by one, so nothing is held. Continuation uses a separate carrier `advance` pattern and the panel setting, with unresolved blockers and pending AI approvals holding it, and never on a page the plan expects questions on that shows none yet and where nothing was done (still drawing). Before it clicks Continue, the kit waits for the page to settle and then reads every answer it filled again. An answer the carrier changed during that wait (a late server response) is not given again: it moves from `filled` to `failed` ("The carrier changed this answer after it was filled; check it."), keeps its `key`, `label` and `order`, is marked failed on the page, adds a `failed:` blocker, and Continue is not clicked.
- A carrier's `stopPages` are pages where the carrier has stopped the quote (Progressive's `DeclinationNotice`: the client already has a Progressive commercial auto policy). The panel shows the carrier's note above the steps, disables Fill this page, and runs no fill, follow-up, helper, Continue, or Luna request there; the page kit refuses them too. The note states the carrier's reason for this client, and each arrival (including a reload) is logged as a `fill_run` with the blocker `stop: <page>`, only once the tab is shown to hold this intake's quote (the layout-readiness evidence); before that the panel says the page may belong to another client.
- A carrier's `quoteState` (`{ pages, key }`: Progressive's home-page `QuoteStateList`, AmWINS' start-page `riskState`) is the control where the quote's state is picked. When the state picked there isn't the intake's garaging state, the panel says so above the steps ([quote-state.js](../src/quote-state.js)), and checks again when the intake is edited. It's a warning only: nothing is filled or held. The pick comes from the agent's or the page's change, from the control as the recorder first sees the page or the panel finds it there (a state the page restored or defaulted; the panel reopened), or from the extension's own fill (AmWINS' risk state; the recorder is paused while filling). It is remembered per tab while the panel is open, and a tab opened from that tab while an intake is loaded inherits it: Progressive opens the quote in a new tab from its home page. So the warning comes back when the intake is cleared and loaded again. A new pick, "<state> is right for this client" (for that intake) or the same tab moving to another carrier ends it (switching to another tab keeps each tab's own pick). A pick made while no intake is loaded isn't seen, because the tab isn't watched then. An intake without a state (an address it couldn't split) is compared with nothing.
- The panel's page strip names the quote step the tab is on, "Step 3 of 7" and a bar, from the carrier's `quoteSteps` ([carriers.js](../src/carriers.js) `quoteProgress`): Progressive's by page name, from the 2026-10-01 walkthrough's order (Filings shows only when filings are asked for; SaveQuote, Quote and AdditionalDetails, whose place wasn't recorded, get no number), AmWINS' by the one-address step heading a fill or the recorder read (`knownStep`; the recorder sends it with field changes, new questions and page arrival), so it follows the step after the next fill, field change or new step drawn. It describes where the tab is; it decides nothing about filling or Continue.
- Steps 2 and 3 show the fill report of the page in front. Reports are kept per tab and page (on a page about one vehicle, trailer or driver, per unit: `stepScope`; on AmWINS, per step, since the address stays), in `state.reports` by `reportKey`, with their DOM nodes, so their buttons and AI cards work again when the page is back in front (`showReport`); a report shown again says the time of its fill. A fill that finishes on a tab not in front keeps its report for that tab (`putReport`) and never shows it on the tab in front. A closed tab's reports go; a new or cleared intake drops them all. A fill problem (an error, a stale intake, a Continue that didn't take, a page with no questions) is said in step 2 of its page's report (`fillProblem`), in words the agent can act on (`fillErrorMessage`: no access, tab closed, page changed or reloaded; the redacted browser message follows).
- While a fill runs, step 2 reads the kit's `progress()` each second ("N answers in so far") and shows **Stop**, which calls the kit's `stop(run)` in every frame: the fill halts as on an agent edit (the answer going in finishes; nothing more is filled; Continue isn't clicked) and the report says "You stopped the fill". A Stop before the fill began is kept too: the panel doesn't ask the kit to fill at all when Stop came while it prepared, and a frame where the fill hadn't started yet keeps the run id (`stoppedRuns`) and halts that fill as it starts. After a fill, step 3 comes into view; after an automatic one, only when the agent isn't working in step 1. An automatic page fill makes the same report as the agent's own, and step 2 says "N filled automatically". An automatic follow-up (`autoFill`) on a page or step that has no report yet is filled as a new page (`fillPage({ auto: 'page' })`): on AmWINS the agent moving on to the next step themselves only reveals new questions at the same address, and that step gets its own report instead of a silent follow-up. On AmWINS, Fill this page reads "again" only once the step in front has a report; a follow-up whose fill reports a step the panel hadn't seen yet (`stepOfResults`) also gets a report of its own. A field of another step that a `hidden` rule fills again (AmWINS' Insured Info prior carriers, blanked after each Save & Continue) is marked `otherStep` by the kit and left out of the step's list and count. A question asked as several boxes (a rule's `group`: AmWINS' auto symbols 1 to 9) is one row in the list, with the boxes ticked; an unticked box that should stay unticked counts as kept, not filled again.
- Step 3 lists what's left for the agent in the order of its fields on the page, whatever kind each item is (unfamiliar, failed, missing, required, differing, check), so the list is the same on every fill: each report item carries `order`, its field's place among the page's questions in document order, read once at the end of the fill (from the last round's questions when a helper opened the next page), and the panel sorts by frame, then `order`. An item with no field on the page (a helper to click by hand, a unit without its row, a field gone since) has no `order` and comes last, as it came. "Answer these on the page" is said once above the items while any is open; an item's own note says only what settled it. **Show on page** on an item with a field (`showOnPage`) asks every frame of its tab to `reveal` the field: it scrolls into view and its mark is ringed for 1.5 s, then the page's own style is put back. Nothing is changed, clicked or focused, and no event is sent; it works only on the item's own tab and page, as Mark done does. A field the page doesn't show now (in a closed section) is said on the item for a few seconds.
- Step 2's **Answers on this page** (`renderReport`) lists the answers by where they came from, under one heading each: from the intake, your edits (filled from a field the agent set or corrected in the panel, its path or one it was worked out from in `agentEdited`: client details, or a Check intake button such as AmWINS' Use Female / Keep Male), TNI standard, already on the page, clicked, yours (not filled: fields the agent answered) (`ANSWER_GROUPS`). Opening the list, or Show all, runs `checkAnswers`: every frame of the tab reads its filled answers back (`readBack`, with the fill's plan steps, so the kit judges each answer as fill does: `agrees`), and a row whose field doesn't hold its answer now is highlighted with what it shows ("Now on the page: …"), counted in the list's summary ("· 2 changed") and announced. An answer the kit says agrees is the same answer however the page wrote it (an address in the page's own format, a ZIP+4); without the kit's word, spacing, case and punctuation are ignored. A follow-up fill's answers are added to the list's count (not listed). A field not on the page now (a closed section) is left as it was. It reads only the page in front, changes nothing, and nothing about it is recorded in usage.
- The kit's `readBack(items)` reads what fields show now, for the panel to check answers against the page. `items` is `[{ key, label }]`, with keys as the fill reports them; `label` tells rows of one question apart, as in `reveal`. It returns `[{ key, label, shown, empty }]` for each field in that frame and leaves out the ones it doesn't find. `shown` has the form of a fill's `shown`: the option text of a list or choice, `checked` or `unchecked` for a checkbox, the text of a box (empty when nothing is picked or typed). `empty` means the field has no answer. It only reads: no value or mark changes, no click, no focus, no event.
- Step 3's "left for you" follows the agent: an item is settled when the recorder reports the agent changed its field on the page (`answeredOnPage`), when the agent accepts an AI answer for it, or with **Mark done** (`markDone`). Mark done adds the field's key to the agent's keys for the page's edit scope, as an edit there does, so no fill changes it and Continue doesn't wait on it; it fills and clicks nothing, and Undo removes the key until the agent answers the field on the page. When nothing is left, Continue stays a click away: the note offers Fill this page again (which clicks Continue under the usual holds), never an automatic click.
- `NEVER_CLICK` and `NEVER_ADVANCE` restrict dangerous actions. Save & Continue is a specific supported continuation exception, not permission for arbitrary Save, Submit, Bind, Buy, Finish, Delete, or report-order actions.
- **Check answers before Continue** (Settings, `check-continue`, saved locally as `checkBeforeContinue`, off by default) sends `hold: true` with every fill. A page the kit would continue is held instead (`report.held = 'check'`): the panel opens Answers on this page and step 3 shows **Looks right, continue** (`continueNote`). Looks right (`lookRight`) reads the top frame's `receipt()` and fills again with it as `confirmed` (never overwriting); the kit clicks Continue only if the page's receipt still equals it after the fill and the wait before Continue, and holds again with `held: 'changed'` otherwise. With the switch on, an item settled since the fill also gets Looks right instead of Fill again and continue, and an automatic follow-up fill that is held shows its report. `receipt()` is a 53-bit fingerprint (cyrb53) of every question's key, label and what it shows in the top frame, as the agent sees it: collapsed fields a fill reads for its `hidden` rules aren't part of it, inside a fill or out, and neither are other steps' hidden fields (`otherStep`); no value leaves the page. Answers inside other frames aren't part of it. The switch is not one of the four filling switches in `fill_run.settings` (the server takes exactly those), and nothing about the hold is logged.
- On one-address applications, the panel checks that the visible step signature changes after continuation. A click is not proof of navigation or of a generated document. A Continue that didn't take (the step unchanged for about 6 s and the page not loading) is clicked once more, silently; when that doesn't take either, automatic filling pauses, the report says "Continue didn't take: click it yourself.", and a `fill_error` (`continue did not take`) is logged. The fill hint under the button says Continue is clicked for the agent only while that setting is on and the carrier has an `advance` pattern; otherwise it says to click Next yourself.
- A fill keeps the context it started with (`fillContext`: its `run` id, tab, carrier, page, the intake and its revision, view, edit scope and the panel's switches), taken before it waits on anything. Auto-advance is refreshed when fill options are built after preparation, so a switch changed while list verification or AI retirement is pending controls that fill and its telemetry; pending AI approval continues to block Continue. A rejected fill logs its rule fingerprint and bounded switches with its redacted error even without a result event. Results that come back after the intake was replaced or corrected are dropped: nothing is remembered, logged or shown as the current intake's, a `fill_error` (`stale: intake changed during the fill`, no client data) is logged and the report says the page may hold the earlier intake's answers. The bookkeeping of a fill whose results come back after the agent moved to another tab goes to the fill's own tab (`rememberFill` writes into that tab's session), including its filled-page and continued-step markers. Its report, helper follow-ups, pending-page fills and Continue watcher never act on the tab now in front; delayed follow-ups and watchers also stop if the intake is replaced or corrected. Driver and trailer list verification checks the captured intake and revision before changing or persisting helper records. A rejected fill from an earlier intake produces the same stale warning, without pausing the current intake or showing the earlier error. Loading a PDF keeps every intake's edit keys and helper records, per intake and tab: the same PDF dropped again finds its own, other intakes' are pruned after 20 intakes or 30 days without being loaded, and Clear forgets the current intake's only (it is done once the helper records are gone too, and restoring helper records waits for a removal still under way, so the same PDF loaded right after a Clear doesn't get them back). Local edit keys and helper records also belong to the browser/extension session: a nonce in [chrome.storage.session](https://developer.chrome.com/docs/extensions/reference/api/storage#property-session) keeps panel reloads and intake switches together, while a browser restart or extension disable, reload or update expires the earlier numeric-tab records before any read or write. Unmarked legacy records expire once too. Initialization is shared under a Web Lock across panels; a failed expiry prevents access until it can be retried. Settings and usage logs are retained. A recorder already in the page is told to resume when the panel attaches, unless a fill or AI apply is under way, so a panel closed mid-fill doesn't leave it paused.

## When the carrier changes

A new question can become unfamiliar; a missing option or rejected answer can become a fill failure. When a known field looks renamed, or at least five questions and 40% of a page are unfamiliar, the fill reports `pageChanged`: the panel says the carrier seems to have changed the page and Continue waits. A renumbering leaves Progressive's questions found (`npm run e2e -- --fixtures --renumber` replays every layout with shifted ids); reworded text or a renamed data-model field leaves that question unfamiliar, never answered as another. Layouts record each field's `ref` (data-model name) since 0.9.9, so a rule can move from text to `field`. Layout capture and rule-coverage reports provide evidence for review. This does not reliably detect a changed meaning under the same data-model name or every changed conditional branch.

Capture the affected scenario and its predecessor answers, classify mapping versus control versus semantic changes, then update a scrubbed fixture and expected outcome. Do not infer applicability merely from a field's presence or absence in one saved page. Use [corrections](corrections.md) for an observed failure and [new carriers](new-carrier.md) for expanded scenario support.
