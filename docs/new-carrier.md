# Adding a carrier or a new supported scenario

Read this when adding a carrier, product, state, or materially different vehicle/coverage flow. A generic label match is not evidence of full support.

## Capture the behavior

Define the initial supported scope: carrier/product, states, operations, vehicle types, driver/vehicle counts, requested coverages, and known exceptions. Reuse existing intake concepts where their meanings agree.

Capture live page layouts and the answers that reveal follow-up questions within the authorized quoting workflow: name a scenario, capture, change one answer, capture again (Capture page layout or Alt+Shift+C), then `npm run captures` for the before/after of each step. Saved HTML/PDFs go in ignored `layouts/`; scrub derived fixtures. A saved page describes one visible state, often without runtime dropdown choices or hidden server-generated branches.

For each discovered question, record its target by a locator the carrier's own code depends on (a data-model name, element id/name, or data-id; GEICO's name is inside element names it renumbers, `Id_<Name>_<n>`, and is used without the number), scoped to its page or step; the question's text is the fallback where there is none and the check elsewhere. A generated number, a position, or a label alone is never a locator. Record also its meaning, options, source of the answer, entity, applicability, and unresolved decisions. Include known combinations that change the flow. Do not infer all conditional behavior from a union of captured fields.

## Implement the adapter

1. Add a module under [src/carriers](../src/carriers/), register it in [carriers.js](../src/carriers.js), and add required hosts to [manifest.json](../manifest.json). Keep `autoFillUrl` (automatic fills) and `layoutUrl` (layouts recorded as the agent works) to the quote's own pages: GEICO's `layoutUrl` leaves out the agents' gateway on the same domain, and its `autoFillUrl` takes the gateway only for its own rules there (the Start New Quote ZIP and the USDOT check; the gateway's other controls are ignored). List the module, and any module it imports, in `RULE_FILES` in [usage.js](../src/usage.js) (a test compares that list with the import graph), and list the intake fields it doesn't read, or reads only through another module, each with its reason, in [the provenance test](../test/provenance.test.mjs).
2. Map confirmed facts and approved scoped defaults. Decide explicitly whether generic fallbacks are suitable; Progressive and GEICO disable them (`useGenericRules: false`; on GEICO they put the first driver in the owner's boxes), and AmWINS keeps them out of its repeating row sections (`rowSections`). A carrier for which TNI has recorded no standard (GEICO) has no `standard` rule and no `supportedClasses`: every question the intake doesn't answer is the agent's. See [intake and rules](intake-and-rules.md) if the scenario needs new facts or exceptions.
3. Implement supported controls and helpers with prerequisites. Use `MAIN` only when page-owned widgets require it (GEICO's design-system radios and buttons are read through open shadow roots in the isolated world); enable batching only with evidence that per-answer server waits are unnecessary. A page drawn with its own web components names their tag prefix as `components` (GEICO's `gds-`), so fills wait for those not defined yet. On a one-address application, keep each helper to its steps (an action's `steps`, and `within` to keep it to one container: GEICO's only helpers add units, each list's add icon and the chooser's Next, `moveOn`; a step that redraws itself after answers, as its Quote & Coverages, can take follow-ups only for questions it draws, `newQuestionsOnlySteps`, and keep what the page took back on automatic fills, `keepTakenBack`, the agent's Fill this page giving it again) and name the steps that are the agent's (`stopSteps`, with the note the panel shows: nothing is filled or clicked there and Luna isn't asked), as `stopPages` does for a page; a screen that is the agent's without a step of its own is named by a button only it shows (`stopButtons`: GEICO's Add USDOT Number). Follow [browser filling](browser-filling.md) for execution changes.
4. Give repeated drivers/vehicles distinct targets and verify entity identity after redraws, imports, or lookups: a row the page may draw in its own order is found by a witness it shows (`witness: { selector, path }`, AmWINS' vehicle rows by their VIN), not by its position, and a helper whose result the page shows (a lookup, an import) carries `verify` (`revealed`, or `{ appears }`) so a click that showed nothing is not counted as done. A step that shows one unit's form at a time (GEICO's Vehicles and Drivers & Incidents: `vehicleSteps`, `driverSteps`) tells its forms apart by a question only that form asks (`whenShown` / `unlessShown`, whose `unit` makes it the form's identity), and the kit holds a form filled for another unit, or a new form when the active unit was filled on an earlier one, until the agent picks the form's unit in the panel (report `unitForm`, `unitHeld`). Preserve questions that need an agent's answer.
5. Add the carrier's supported standards to [tni-rules.js](../src/ai/tni-rules.js) when AI assistance is in scope; a new section also needs `evidenceFor` in [common.js](../src/ai/common.js) to give it to that carrier, which today splits the rulebook for Progressive and AmWINS only. GEICO has none (no TNI standard is recorded), so Luna gets the scoped intake there and no TNI rules. AI availability does not make the carrier fully supported.
6. When the quote's step order has been observed, list it as `quoteSteps` (each step's `pages`, or its one-address `step`) for the panel's page strip; leave out pages whose place in the flow wasn't seen. Without it the strip shows only the carrier. A one-address application lists its step names as `layoutSteps`: pagekit reads the step from the visible headings (AmWINS) or from a progress bar's part under way while the page title names it too (GEICO), and rules (`steps`), actions, stop steps and logged events name steps by those names.

## Validate and expand

Use saved-page behavior mocks where practical, as with AmWINS and GEICO, or layout replays for server-backed pages, as with Progressive. A single-page application can be one fixture file for the whole quote, as GEICO's is: each step an inert template its mock script swaps in, built from the ignored saved pages by a script that writes nothing on a privacy finding, with a test that holds the committed file to the same rules on machines without the raw pages. Include known expected answers, branch triggers, rejection/redraw behavior, manual corrections, missing information, and no-final-submission checks. Add the relevant checks to CI for maintained support.

Test the initial supported scenarios and the known exceptions, including a nearby combination where a rule must not apply. Mock success does not prove live backend acceptance or complete product coverage. Use a supervised pilot for live-only behavior; document unsupported questions instead of generalizing from one successful quote.

After pilot runs, inspect `npm run coverage` and agent reports. Use [learning](learning.md) for candidate discovery and [corrections](corrections.md) for fixes. Expand support when new scenarios are validated; this document does not automatically start another carrier or release milestone.
