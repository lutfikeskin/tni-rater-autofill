# Testing and release verification

Read this when choosing checks, changing a harness or baseline, or preparing an authorized release.

## Choose checks for the change

The extension uses plain ES modules with no source build step. `npm ci` installs locked development dependencies on Node.js 22; `npm test` runs `node:test` files under `test/`. Run a focused file with `node --test test/pagekit.test.mjs`. That file runs the real fill engine in a vm context on a virtual clock: the context's `setTimeout`, `clearTimeout` and `Date` come from the harness, and the clock moves to the earliest due timer whenever the event loop would otherwise idle, one timer per turn, so the engine's settle, retry and quiet-period waits keep their tick counts and order but take no real time (the file took 150 s on real timers; it takes under a second). A test whose page changes "later" sets its timer in the file, on the same clock. Browser runners use Playwright Chromium (`npx playwright install chromium` once when needed).

| Affected behavior | Relevant checks |
| --- | --- |
| Intake extraction or cleanup | `test/normalize.test.mjs`, `test/intake-regressions.test.mjs`, `test/intake-forms.test.mjs` (the pre- and post-2026-10 intake forms), `test/intake-source.test.mjs` (where answers are on the PDF, the page strip's step order); affected synthetic intake cases |
| Progressive rules or page execution | `test/progressive.test.mjs`, `test/pagekit.test.mjs`, `npm run e2e -- --fixtures` |
| AmWINS rules or application flow | `npm run mock:amwins` before completing an AmWINS rule change |
| Panel orchestration or packaged behavior | `test/sidepanel-safety.test.mjs`, `npm run e2e:extension` |
| AI validation, approvals, caching | `test/luna.test.mjs`, `test/ai-eval.test.mjs`, `npm run mock:luna` |
| Events, learning, layout coverage, transport | Corresponding `usage`, `usage-log`, `learn`, `coverage`, `conditions`, `weekly-signals`, `server`, and `consistency` test files |
| Rule changes measured on recorded quotes | `test/benchmark.test.mjs`; locally, `npm run benchmark -- --intakes <folder> --save <file>` on `main` and again with `--against <file>` on the branch ([learning](learning.md)). It needs the quotes' intake PDFs on this computer and reports agreement with past agents, not live accuracy |
| Manual page captures and their report | `test/pagekit.test.mjs` (capture), `test/sidepanel-safety.test.mjs` (panel), `test/captures.test.mjs` (`npm run captures`) |
| Documentation only | Link/command checks, current-code audit, and `git diff --check`; no browser run or version bump |

Run `npm test` for code changes, plus affected integration checks. Repeat or broaden only for new changes, failures, or unresolved concerns. Do not add tests that merely mirror a low-impact edit.

## Browser harnesses and limits

- `npm run e2e` runs Progressive layout replays (locally, `npm run ci`, and in the Windows smoke when dispatched); `--fixtures` uses committed per-state fixtures for local verification; `--renumber` shifts every question id as Progressive did on 2026-10-07, and every page outcome must equal the baseline: what each question got, by its text and, for a filled one, the rule that filled it (its name, the question id it was written for and its intake path, never the page's number), so two controls reading the same that swap answers differ (a hash per page), failures, counts, blockers, and the helpers clicked in order. In every mode the baseline comparison flags fewer fills, new failures, more unmapped or left-for-agent questions, more blockers, a lost Continue, and a page whose outcomes hash changed: a question that got another answer with the counts unchanged fails the run until the change is reviewed and accepted with `--update`. The replay page loads ExtJS 6.2.0 from cdnjs, and the AmWINS fixture loads Bootstrap 5.3.3 from jsdelivr, each with a `sha384` `integrity` attribute and `crossorigin="anonymous"`: a changed CDN file fails to load instead of running, and a deliberate upgrade needs the new digest in the tag (the ExtJS theme stylesheet's own `@import`s are not covered). Fixture fields carry `ref` (the data-model name) where it is known. The replay's sample intake takes the layout's state (a state's own answers, such as Florida's PIP). The replay draws each field in its recorded Duck Creek row (`row`, else the first), so the fill tells each vehicle's and trailer's Rates row apart. The sample intake gets the layout's units: as many vehicles as its context recorded and a trailer when it had trailers, more when a page's rows show more units (trailers on a layout with trailers, else vehicles; of two pages naming as many units, the one with rows); extra vehicles repeat the sample's with another VIN, and the trailer is made up. With several units, each takes its row's year, make and model, and each row is drawn under that one name. A field named after a unit but recorded before rows, on a page whose units have rows, is drawn apart from them ([units.js](../test/replay/units.js), `test/replay-units.test.mjs`). An intake chosen on the replay page is used as it is, only cut to the layout's vehicle count; the sample is never cut. Answers are kept under the question id, with the row only past a page's first row, as the bakeoff scorer reads them. A replay with several units checks that each row is found, not that a unit's own answers (type, value) match the recorded quote. Local runs can also include captures and generated layouts. A replay does not establish complete live navigation, server acceptance, or real lookup reliability.
- `npm run mock:amwins` checks the saved-site behavior mock and its expected answers, including continuation and no submission.
- `npm run e2e:extension` needs `npm run package` and `npm run replay` serving on port 8792. It runs the packaged panel/extension on the AmWINS mock, focusing the panel or carrier tab before native UI input. It verifies that missing client facts remain blank and hold Continue, supplies explicit synthetic agent answers through trusted browser input, and resumes through the panel. It reads back the recorder's saved protection keys after trusted edits, then waits for a fresh report from the ordinary Fill action (retrying a click only while an automatic fill prevented it from starting). It never writes protection keys or answers the same control twice; missing holds, missing recorder acknowledgment, or a report that never settles still fail the bounded run. It checks that those answers survive carrier reloads, returning to the previous step stays there, and the declaration and Submit remain untouched. Before the panel opens, it sets the panel's Server setting to a throwaway local usage server (`server/index.mjs` on a temporary folder), so its usage events never reach the pilot's data. It blocks and fails on any request to the production usage server, and fails if `intake_loaded` doesn't reach the local one. `npm run mock:luna` instead blanks the Server setting (uploads off). A new harness that loads the packaged extension needs one of these: the extension uploads to production by default.
- `npm run mock:luna` also needs the package. It intercepts OpenAI requests and checks the dedicated key field, Luna's independent automatic-selection setting, the approval hold and reload retention, rejection/manual correction, conflicting evidence and stale provider responses, that facts left to the agent (`manualOnly`) never reach Luna, and that Mark done on them lowers what's left without a refill while a pending approval still holds Continue. It also checks the intake-load checks: one claims-box review and one driver first-name check per intake (the latter sending first names only), with no second claims-box review when the panel reopens on the same intake, the general-liability and driver-gender items on Check the intake with buttons that save the agent's edit, and that with assistance off neither request is sent and no item appears. It confirms Clear's question before each new intake. The mock makes no live AI requests.
- The Luna mock should also preserve the request-budget contract: low reasoning and low verbosity, no `temperature` or `top_p`, up to 12 eligible fields per adaptive request, a combined state/schema bound of 48,000 characters, 4,096-token choice output, 2,048-token verification output, and the complete evidence/scoped-intake split between the two calls. Before verification, the planner must bound the whole scoped intake, keep at most four cited sources per field, include the longest visible answer in its size estimate, split oversized groups, and reject a single oversized field for manual review. These caps bound request work; they do not measure billed tokens, live latency, or live accuracy.
- Usage assertions should cover `tokensIn`, `tokensOut`, `modelCalls`, `reasoningTokens`, `cachedTokens`, and `cacheWriteTokens`. Reasoning is included in output tokens, while `modelCalls` counts logical provider calls and excludes HTTP retries. Controlled mocks can verify the counters and boundaries; they cannot establish live performance.
- Schema checks should cover the shared citation definition and adaptive splitting at 1,000 total enum values, preserving all options and sources.
- `npm run ai:eval -- --score <saved-result.json>` scores saved Luna output. Live evaluation is explicit with `--live` and `OPENAI_API_KEY`; the evaluation agent chooses when to run it. Committed cases are synthetic and not expert-reviewed; they are a starting scaffold, not a production accuracy claim.
- `npm run test:intakes -- --carrier amwins --cases 03,09` selects synthetic cases. The pool under `dist/synthetic-intakes` is local and untracked; read [intake-mocks.mjs](../scripts/intake-mocks.mjs) for available options. With `--lookup-check`, timeout cases verify the injected timeout followed by a successful automatic retry inside the initial fill, exactly two attempts, and no additional manual click. Missing pool data is a stated limitation, not evidence of a pass.

## Baselines and fixtures

For relevant new Progressive captures: build layouts with `npm run layouts`, review them (and `npm run transitions` for their conditions, `npm run captures` for manual before/after captures), and use `npm run fixtures:progressive` to refresh scrubbed fixtures. Fixtures with `showWhen` make the replay hide those follow-ups until their trigger has a matching answer, as the live page does, so expect baseline changes when refreshing them. Review the expected behavior before accepting `npm run e2e -- --update`; a baseline is not an answer key. Preserve unrelated baseline entries.

For AmWINS page changes, update the scrubbed [fixtures](../test/fixtures/amwins/) and expected answers in [amwins-mock.mjs](../scripts/amwins-mock.mjs). Retain branch behavior rather than only static markup.

## CI and authorized releases

[checks.yml](../.github/workflows/checks.yml) runs unit tests and packaging on Ubuntu for pull requests, with a five-minute limit and cancellation of superseded runs. [windows-smoke.yml](../.github/workflows/windows-smoke.yml) installs Playwright Chromium on Windows and checks native ZIP extraction, normal/reversed AmWINS, committed Progressive fixture replays, the Luna mock and packaged-extension E2E with the Node replay server. It runs only when dispatched by hand (fifteen-minute limit). `npm run ci` ([ci-local.mjs](../scripts/ci-local.mjs)) runs the same steps on a local Windows computer, in the same order (the ZIP check with fflate instead of `Expand-Archive`, the installed `node_modules` instead of `npm ci`, a replay server already on port 8792 reused); `npm run ci -- --quick` runs only the unit tests and package. The repository is private, so GitHub bills its runs (Windows minutes double): Windows is checked locally before pushing, and the Windows smoke is dispatched only when a run on GitHub is wanted. These checks need no production credentials. Local runs remain required for affected behavior; see [Windows setup](windows-development.md). Merging a tested PR avoids a duplicate main-branch run. Do not claim CI passed based only on local tests.

[claude-review.yml](../.github/workflows/claude-review.yml) has Claude review a pull request once when it opens, reopens or leaves draft: inline comments marked Blocker, Should fix or Nit, then one summary comment. It only reads and comments. [claude.yml](../.github/workflows/claude.yml) answers `@claude` in PR and issue comments from people with write access: `@claude review` reviews again after new pushes, and `@claude fix the review comments` pushes fixes to the PR branch after running `npm test`. Both use the Claude GitHub App and the repository secret `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`); without it they fail without affecting the checks above. A Claude review is a second opinion, not a substitute for the checks or the maintainer's review.

For a shipped extension version, keep [manifest.json](../manifest.json) and [package.json](../package.json) in sync and update the lockfile's package metadata. `npm run package` produces the zip and unpacked directory under ignored `dist/`; both stamp the page scripts with their build, and only the unpacked copy carries the fixed development extension key (`scripts/lib/package.mjs`), which the store zip must not. A local correction or documentation change does not itself authorize a version bump or upload.

Use [store release](chrome-web-store.md) only for distribution, and [hosting](hosting.md) only for server deployment. Verify the requested outcome, including retained page values or a generated document when that is part of the task; distinguish mock, packaged-extension, and live evidence.

For the provider's general guidance, see the official [GPT-6 Luna model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna), [latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist), and [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching). A passing mock confirms the request shape and integration behavior only; it does not establish a production latency or cost improvement.
