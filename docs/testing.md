# Testing and release verification

Read this when choosing checks, changing a harness or baseline, or preparing an authorized release.

## Choose checks for the change

The extension's files are plain ES modules that run as written, except the side panel: Vite ([vite.config.js](../vite.config.js)) bundles `sidepanel/sidepanel.html` and everything it imports (the panel, `src/`, PDF.js) into each packaged copy, unminified and with source maps, and stamps its copy of `usage-log.js` with the copy's channel and commit: `store` for the store zip, `unpacked` for any other build, `npm run panel` included (the commit is `+dirty` when the packaged files, `vite.config.js` or the package files have uncommitted changes, and always after `npm run panel:watch`). The package keeps the panel's sounds and images, which it names at run time, and leaves its source `.js`, `.html` and `.css` out. `npm run panel` rebuilds only the panel in `dist/tni-rater-autofill` (after one `npm run package`), and `npm run panel:watch` does so on every save; reload the panel to see it. The extension can't load from a dev server, so Load unpacked uses `dist/tni-rater-autofill`, not the repository. `npm ci` installs locked dependencies on Node.js 22; `npm test` runs `node:test` files Run a focused file with `node --test test/pagekit.test.mjs`. That file runs the real fill engine in a vm context on a virtual clock: the context's `setTimeout`, `clearTimeout` and `Date` come from the harness, and the clock moves to the earliest due timer whenever the event loop would otherwise idle, one timer per turn, so the engine's settle, retry and quiet-period waits keep their tick counts and order but take no real time (the file took 150 s on real timers; it takes under a second). A test whose page changes "later" sets its timer in the file, on the same clock. Every fill in that file is held, as it returns, to the review invariant ([Only what is on the page](browser-filling.md#only-what-is-on-the-page): each item left for the agent and each answer listed is on the page, known off screen or said gone, and what it says the page shows is the page's, read with the kit's `present`; `assertLive`), and its last test checks that this covered the file's fills. Browser runners use Playwright Chromium (`npx playwright install chromium` once when needed). `npm run lint` runs [oxlint](https://oxc.rs/docs/guide/usage/linter) with [.oxlintrc.json](../.oxlintrc.json): its correctness rules and `no-undef` (a name used without being declared or imported, such as a panel function moved to another part without its import) as errors, with unused function parameters, caught errors and rest-sibling omissions allowed, and its stylistic suggestions off; the two vendored PDF.js files are not linted. A deliberate exception takes an `oxlint-disable-next-line <rule> -- <why>` comment.

`npm run preview` (Vite's dev server on `http://127.0.0.1:5180`, also `panel-preview` in [.claude/launch.json](../.claude/launch.json) for the Claude desktop app's browser pane) shows the panel from the source beside a practice carrier page (the AmWINS and GEICO fixtures, the Progressive mock), as one Chrome tab with the panel open. [preview/](../preview/) answers the panel's `chrome.*`: its storage (kept in the preview page, gone when it reloads), the one tab, the injected page scripts (each run with a `window` whose `top` is the carrier page, as in a tab of its own) and their messages. So a fill runs as in the extension, and **Load sample intake** loads `test/fixtures/sample-intake.pdf`. After a panel edit only the panel reloads, keeping its intake. Uploads start off and the panel's `fetch` requests to any other origin are refused, a local server on another port (`npm run server`) included; the panel sends with `fetch`, and other request APIs aren't guarded. The preview is for seeing and changing the panel; it proves nothing about the packaged extension or a live carrier (use the [verify skill](../.claude/skills/verify-tni-rater/SKILL.md)).

`npm run typecheck` runs TypeScript's checker (`tsc -p .` with [tsconfig.json](../tsconfig.json)) on the JavaScript as it is: nothing is compiled or emitted, and Chrome, the tests and the package keep using the files unchanged. Every JavaScript file of the extension, the server, the scripts and the tests is read (`include`), and only a file that opts in with `// @ts-check` is checked: today [plan.js](../src/plan.js), [usage.js](../src/usage.js), [normalize.js](../src/normalize.js), [carriers.js](../src/carriers.js), the carrier modules and [types.js](../types.js) itself (a misspelled type name there would otherwise turn its field's check off). A file under `server/`, `scripts/` or `test/` runs on Node: opting one in needs Node's types (`@types/node`) first, which aren't installed, since in this one program they would also let the extension's files use Node's APIs unflagged. They name the shapes passed between parts from [types.js](../types.js), JSDoc comments only: a carrier's settings, rules, actions and Continue, the plan's steps, the fill's options and report, and the usage events `src/usage.js` builds. A misspelled or undeclared key in a carrier's rule or action, a report or event field read under an old name, or a value of the wrong kind fails the check; how a carrier page behaves doesn't (that is for the mocks and live runs). `strict` is off. [pagekit.js](../src/content/pagekit.js) and the side panel ([sidepanel/](../sidepanel/)) aren't checked yet; the functions that make or read those shapes are annotated. A rule or action built in a `.map(...)` callback is checked only through the callback's `/** @returns {CarrierRule} */` (or `CarrierAction`), and only if what it spreads is typed: spreading an `any` makes the whole object `any`. A list written inline in front of `.map(...)` isn't checked at all (a comment can't type that array, and a cast would add parentheses to the code), so a list of rules goes to a helper that takes `CarrierRule[]` instead: AmWINS' `perRow`, GEICO's `named` and `on`, Progressive's `onPage`. `types.js` sits at the repository's root, outside the folders the package takes, and `test/package.test.mjs` keeps it comments only and imported by no module of the extension.

## Browser harnesses and limits

- `npm run e2e` runs Progressive layout replays (locally, the pull-request checks on Ubuntu, and the Windows smoke when dispatched); `--fixtures` uses committed per-state fixtures for local verification; `--renumber` shifts every question id as Progressive did on 2026-10-07, and every page outcome must equal the baseline: what each question got, by its text and, for a filled one, the rule that filled it (its name, the question id it was written for and its intake path, never the page's number), so two controls reading the same that swap answers differ (a hash per page), failures, counts, blockers, and the helpers clicked in order. In every mode the baseline comparison flags fewer fills, new failures, more unmapped or left-for-agent questions, more blockers, a lost Continue, and a page whose outcomes hash changed: a question that got another answer with the counts unchanged fails the run until the change is reviewed and accepted with `--update`. The replay page loads ExtJS 6.2.0 from cdnjs, and the AmWINS fixture loads Bootstrap 5.3.3 from jsdelivr, each with a `sha384` `integrity` attribute and `crossorigin="anonymous"`: a changed CDN file fails to load instead of running, and a deliberate upgrade needs the new digest in the tag (the ExtJS theme stylesheet's own `@import`s are not covered). Fixture fields carry `ref` (the data-model name) where it is known. The replay's sample intake takes the layout's state (a state's own answers, such as Florida's PIP). The replay draws each field in its recorded Duck Creek row (`row`, else the first), so the fill tells each vehicle's and trailer's Rates row apart. The sample intake gets the layout's units: as many vehicles as its context recorded and a trailer when it had trailers, more when a page's rows show more units (trailers on a layout with trailers, else vehicles; of two pages naming as many units, the one with rows); extra vehicles repeat the sample's with another VIN, and the trailer is made up. With several units, each takes its row's year, make and model, and each row is drawn under that one name. A field named after a unit but recorded before rows, on a page whose units have rows, is drawn apart from them ([units.js](../test/replay/units.js), `test/replay-units.test.mjs`). An intake chosen on the replay page is used as it is, only cut to the layout's vehicle count; the sample is never cut. Answers are kept under the question id, with the row only past a page's first row, as the bakeoff scorer reads them. A replay with several units checks that each row is found, not that a unit's own answers (type, value) match the recorded quote. Local runs can also include captures and generated layouts. A replay does not establish complete live navigation, server acceptance, or real lookup reliability.

- `npm run e2e:extension` needs `npm run package` and `npm run replay` serving on port 8792. It runs the packaged panel/extension on the AmWINS mock, focusing the panel or carrier tab before native UI input. The sample intake answers every client fact AmWINS asks and TNI's standards answer the rest, so before filling it clears the second driver's marital status in the panel's All client details drawer (as an agent correcting the intake would): that row's marital status, a client fact the intake now leaves blank (`clientFact` in [amwins.js](../src/carriers/amwins.js)), is the agent's. It verifies that the missing fact remains blank and holds Continue on Drivers, supplies an explicit synthetic agent answer through trusted browser input (DIVORCED, neither the PDF's answer nor the first driver's, so a refill from the intake or the wrong row shows), and resumes through the panel. A hold that never comes fails the run ("Manual hold wasn't exercised"): if a TNI standard ever answers the question cleared here, clear another client fact rather than drop the hold (the run lost it once, when valued loss runs became a standard on 2026-10-19). It reads back the recorder's saved protection keys after trusted edits, then waits for a fresh report from the ordinary Fill action (retrying a click only while an automatic fill prevented it from starting). It never writes protection keys or answers the same control twice; missing holds, missing recorder acknowledgment, or a report that never settles still fail the bounded run. It checks that those answers survive carrier reloads, returning to the previous step stays there, an earlier step's answers open read-only from the list's page menu, the panel opened in its own window (Pop out) replaces the copy that was open, lists the earlier steps' reports kept in session storage in its page menu before filling anything (W43-39), follows the AmWINS tab and fills it, **Back to the side panel** opens Chrome's side panel and closes the window, a window popped out again closes that side panel (Chrome's side panel is no page Playwright shows: the run counts them with `chrome.runtime.getContexts`), and the declaration and Submit remain untouched. The panel runs at a side panel's size (400 × 860), and the run fails if the panel's document ever scrolled (only its middle and dock may: W44-10). Given a folder (`npm run e2e:extension -- <folder>`), it saves screenshots there: the panel, the client details drawer and an earlier step, the last two also at side-panel width, and the panel in its own window. Before the panel opens, it sets the panel's Server setting to a throwaway local usage server (`server/index.mjs` on a temporary folder), so its usage events never reach the pilot's data. It refuses and fails on any request that leaves the machine (a host other than localhost: the production usage server, an AI provider, a CDN), and fails if `intake_loaded` doesn't reach the local one, or `intake_profile` doesn't reach it whole (with fields in `dropped`, the server and the extension disagree on its shapes). What the mock page's own HTML loads (the captured page's Bootstrap from a CDN, and its Intercom frame, which wasn't saved with it) is refused or missing too, but isn't counted: the run needs no network. It also fails on any console error or uncaught exception in the panel (as a page or popped out), the mock tab or the service worker (`ctx.on('console')`, `ctx.on('weberror')`, the worker's `console`), except those on `BENIGN`: the failed loads of the mock page's own assets. It waits on what the mock and the panel do, never a fixed time: `quiet()` waits until every Save & Continue's background save has reloaded the steps, the mock's loading overlay is gone, no fill runs, and nothing of these has changed for a second. It uses longer quiet windows where it checks that nothing happens: 1.5 s for the hold before the agent answers, and 4 s after Prev. `npm run mock:luna` instead blanks the Server setting (uploads off). A new harness that loads the packaged extension needs one of these: the extension uploads to production by default.
- `npm run mock:geico` also opens two quote pages of its own, each with the extension's world: GEICO's "Add USDOT Number / Skip" screen after Business & Owner Info (`?usdot=ask`, W43-27; never captured, its two buttons only), whose layout must be read as that stop screen (`stopScreen`), where a fill fills and clicks nothing and the agent's Skip goes on; and the gateway's Start New Quote ZIP (`?gateway=<zip>`, W43-28), where a ZIP carried over from the last quote must be replaced with the intake's and one the agent then types, reported by the recorder as theirs, kept and unflagged by the next fill. Another, a fresh Quote & Coverages with trailer interchange and general liability on the intake (TNI, 2026-10-28), must open both cards by their chevrons (never Non-Owned Trailer Physical Damage's), answer them with TNI's answers ($50,000 as "$60k/$1000 deductible"), mark the number of trailers, the trailer type and that limit to confirm, and click Recalculate once only after the agent confirms them. With the filling time it prints what making each fill's report agree with the page cost (pagekit `reconcile`: the time, the page reads, the items dropped, the answers gone and the choices given again), and under each fill the answers whose question has gone from the page.
- `npm run mock:luna` also needs the package. It intercepts OpenAI requests and checks the dedicated key field, Luna's independent automatic-selection setting, the approval hold and reload retention, rejection/manual correction, conflicting evidence and stale provider responses, that facts left to the agent (`manualOnly`) never reach Luna, and that Mark done on them lowers what's left without a refill while a pending approval still holds Continue. It also checks the intake-load checks: one claims-box review and one driver first-name check per intake (the latter sending first names only), with no second claims-box review when the panel reopens on the same intake, the general-liability and driver-gender items on Check the intake with buttons that save the agent's edit, and that with assistance off neither request is sent and no item appears. It confirms Clear's question before each new intake. The mock makes no live AI requests.
- The Luna mock should also preserve the request-budget contract: low reasoning and low verbosity, no `temperature` or `top_p`, up to 12 eligible fields per adaptive request, a combined state/schema bound of 48,000 characters, 4,096-token choice output, 2,048-token verification output, and the complete evidence/scoped-intake split between the two calls. Before verification, the planner must bound the whole scoped intake, keep at most four cited sources per field, include the longest visible answer in its size estimate, split oversized groups, and reject a single oversized field for manual review. These caps bound request work; they do not measure billed tokens, live latency, or live accuracy.
- Usage assertions should cover `tokensIn`, `tokensOut`, `modelCalls`, `reasoningTokens`, `cachedTokens`, and `cacheWriteTokens`. Reasoning is included in output tokens, while `modelCalls` counts logical provider calls and excludes HTTP retries. Controlled mocks can verify the counters and boundaries; they cannot establish live performance.
- Schema checks should cover the shared citation definition and adaptive splitting at 1,000 total enum values, preserving all options and sources.
- `npm run ai:eval -- --score <saved-result.json>` scores saved Luna output. Live evaluation is explicit with `--live` and `OPENAI_API_KEY`; the evaluation agent chooses when to run it. Committed cases are synthetic and not expert-reviewed; they are a starting scaffold, not a production accuracy claim.
- `npm run test:intakes -- --carrier amwins --cases 03,09` selects synthetic cases. The pool under `dist/synthetic-intakes` is local and untracked; read [intake-mocks.mjs](../scripts/intake-mocks.mjs) for available options. With `--lookup-check`, timeout cases verify the injected timeout followed by a successful automatic retry inside the initial fill, exactly two attempts, and no additional manual click. Missing pool data is a stated limitation, not evidence of a pass.

## CI and authorized releases

[checks.yml](../.github/workflows/checks.yml) runs the checks on Ubuntu for pull requests, in parallel jobs, with superseded runs cancelled: lint, the type check, unit tests and packaging (`checks`, five-minute limit); the store ZIP extracted with `unzip` and checked (no development key, the source's version, and the built side panel), then the packaged-extension E2E with the Node replay server on port 8792 (`Packaged extension`, ten minutes); and one job each for the AmWINS mock, AmWINS reversed, the GEICO mock, the committed Progressive fixture replays against `test/e2e-baseline.json` and the Luna mock (ten minutes each). Each browser job installs only Playwright's Chromium (`npx playwright install chromium`): the runner image's preinstalled Chrome already brings its system libraries, and `--with-deps` fetched them again from Ubuntu's mirror, once for 9 minutes, timing a job out. The workflow reads the repository only (`contents: read`) and uses no secrets, so a pull request from a fork runs it without reaching `CLAUDE_CODE_OAUTH_TOKEN` or `RATER_ADMIN_TOKEN`; it uploads no artifacts, and its logs are public. [windows-smoke.yml](../.github/workflows/windows-smoke.yml) runs the same browser steps on Windows, in one job, and checks the ZIP with `Expand-Archive`. It runs only when dispatched by hand (fifteen-minute limit). The repository has been public since 2026-10-27, so these runs, Windows included, cost nothing, and the maintainer decided that day that GitHub's Checks replace local CI: **a pull request is ready to merge when every job of its Checks passed on its head commit** (`gh pr checks <n>`). While writing code, run `npm test` and the focused checks the table above names for what changed. To reproduce a failing job, run that job's own command from the workflow (`npm run mock:geico`, `npm run e2e:extension` after `npm run package`, and so on). The local CI script (`npm run ci`) and the pre-push hook were removed on 2026-10-31, since the Checks replace them. The tests that run git still pass an environment without git's per-repository variables (`gitEnv` in [ledger.mjs](../scripts/lib/ledger.mjs)): a hook once let a test's `git init` reach the repository through the hook's `GIT_DIR`. Windows is checked by dispatching the Windows smoke ([Windows setup](windows-development.md)). These checks need no production credentials. Merging a tested PR avoids a duplicate main-branch run. Do not claim CI passed based only on local tests.

[CodeRabbit](https://coderabbit.ai) automatically reviews pull requests that are not drafts (trial from 2026-10-30, settings in [.coderabbit.yaml](../.coderabbit.yaml)); `@coderabbitai review` asks it again. [claude-review.yml](../.github/workflows/claude-review.yml) has Claude review a pull request once when it opens, reopens or leaves draft: inline comments marked Blocker, Should fix or Nit, then one summary comment. It only reads and comments, and runs alongside CodeRabbit (it was paused on 2026-10-30, when the maintainer's Claude usage ran out, and turned back on 2026-10-31). [claude.yml](../.github/workflows/claude.yml) answers `@claude` in PR and issue comments from people with write access: `@claude review` reviews again after new pushes, and `@claude fix the review comments` pushes fixes to the PR branch after running `npm test`. Both use the Claude GitHub App and the repository secret `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`); without it they fail without affecting the checks above. A Claude review is a second opinion, not a substitute for the checks or the maintainer's review.

For a shipped extension version, keep [manifest.json](../manifest.json) and [package.json](../package.json) in sync and update the lockfile's package metadata. `npm run package` produces the zip and unpacked directory under ignored `dist/`; both stamp the page scripts with their build, and only the unpacked copy carries the fixed development extension key (`scripts/lib/package.mjs`), which the store zip must not. A local correction or documentation change does not itself authorize a version bump or upload.

Use [store release](chrome-web-store.md) only for distribution, and [hosting](hosting.md) only for server deployment. Verify the requested outcome, including retained page values or a generated document when that is part of the task; distinguish mock, packaged-extension, and live evidence.

For the provider's general guidance, see the official [GPT-6 Luna model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna), [latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist), and [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching). A passing mock confirms the request shape and integration behavior only; it does not establish a production latency or cost improvement.
