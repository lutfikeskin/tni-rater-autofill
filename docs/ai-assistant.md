# AI assistance

Read this when changing AI suggestions, prompts, response validation, context reuse, or agent approval.

## Current role

The rules engine fills first. AI only handles the small remainder: unresolved radio, select and checkbox questions (`unknown`, `failed`, `noData`, `leftRequired`) where no exact carrier mapping applies. It does not audit already-filled answers, produce typed text, click, navigate, look anything up, or submit.

The assistant uses OpenAI **GPT-6 Luna** at `https://api.openai.com/v1/responses`. The brain button opens Settings at **Assistant**: **Add key**, paste the OpenAI API key and **Save** (or Enter; nothing is saved while it is typed), then turn on **Suggest answers**. The model is fixed and not shown for editing. Settings are per-device: `aiOn`, `lunaKey`, and `lunaAuto`; the fixed model is `gpt-6-luna`. They live in `chrome.storage.local`, which `background.js` restricts to the extension's own pages (`setAccessLevel('TRUSTED_CONTEXTS')`); Chrome honours that for local storage from version 140, the manifest's `minimum_chrome_version`, so content scripts cannot read the key. Legacy provider settings are ignored and never used as an OpenAI key. Assistant use and automatic selection are off unless the agent enables them. Saved automatic decisions from a retired assistant remain holds for manual review and cannot release Continue by themselves. Decisions saved under an earlier policy version (v3, before the 2026-10-09 answer-provenance rulebook) are retired the same way.

Luna policy v4 (`luna-evidence-v4`, `POLICY_VERSION` in `src/ai/luna.js`) uses the fixed `gpt-6-luna` model, low reasoning, low text verbosity, strict Structured Outputs, `store: false`, and no tools, `temperature`, or `top_p`. The deployment checklist requires omitting those sampling controls when reasoning is enabled. It reviews up to 12 eligible fields per adaptive request, with a combined state and schema bound of 48,000 characters. Choice output is capped at 4,096 tokens and verification output at 2,048 tokens; these are request budgets and do not represent actual billed token counts. The first call carries the complete bounded fact/rule source set once without duplicating the intake representation. The verification call carries the whole scoped intake and the evidence cited by the proposed choices. Both calls are required for a non-`leave` result. The same local answer cache is used; no extended paid API cache configuration is enabled.

Luna suggests current visible options with source IDs and a short explanation. Missing information, conflicts, absent/unknown evidence, invalid options, refusals, incomplete output, and unexpected models fail closed. The verification call checks each proposed option against its sources and intake. This is another judgment from the same model, not independent proof. Luna automatic selection is separately opt-in through `lunaAuto`; it can pick only a visible, applicable radio/select/checkbox choice when the verification succeeds, the choice differs from the current value, and the field is outside the manual-only safety list. It never displays a generated confidence percentage. Two judgments from the same model are not calibrated accuracy evidence. This request-budget change is intended to reduce prompt and output work; live latency, cost, and accuracy have not been measured. See the [model documentation](https://developers.openai.com/api/docs/models/gpt-6-luna), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist), and [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) for the provider contract and general optimization guidance.

Before any paid model request, the planner conservatively sizes the possible verification request: the whole scoped intake, at most four cited sources per field, and the longest visible answer. It splits a group when that bound is exceeded; a single field that is still too large is rejected for manual review. This keeps the evidence boundary explicit while avoiding a request that only fails after it reaches the provider.

The proposal schema shares the exact source-ID constraint through `$defs`/`$ref` instead of repeating it for every field. Groups also split before exceeding the Structured Outputs limit of 1,000 total enum values; no visible option or source is removed to fit a group.

The historical request shapes explain the scope of the optimization. The earliest Luna path used low reasoning and one request for up to 40 fields with an 8,000-token cap. The prior evidence-checked path used medium reasoning, up to four fields per batch, and two calls per batch with an 8,192-token cap. The optimized path uses low reasoning, up to 12 fields per batch, and two calls with 4,096/2,048-token caps. Twelve eligible fields therefore move from up to six calls to two when there are no size splits, retries, abstentions, or cache hits.

Luna also reads the intake's claims box once per intake (on the 2026-10 form, the claims box and the Additional Notes box as one text, `intakeNotes`), when assistance is on and the key is set. Code splits the box into lines (at most 20) and replaces client names, numbers and the street (`redactionTerms`) before one structured call answers per line: does it name non-trucking liability (NTL / bobtail), does it ask for coverage other than the form's ticked coverages, and how many years the business has operated or the year it started, as the line states them (integers or null; Luna copies, never calculates). Flagged lines become Intake check items (`ai.ntl`, `ai.coverage-change`) quoting the line; code turns a start year into years and adds `ai.years-in-business` for the first line stating them when they differ from the intake's years in business (or years under own authority), including a blank one, which AmWINS otherwise quotes as a new venture ("in Biz for 3+ years" with no year established); a line the intake's own NTL check already quotes isn't repeated. Nothing is filled or ticked from them: the agent changes Requested coverage. There is no second verification call because nothing is applied. A malformed answer fails the whole review, and a failed review adds an Intake check item to read the box by hand; it is tried again when the assistant settings change (also when they change while a review is still out). An answer for a claims box or form coverages that changed meanwhile is dropped and the box read again; an edit to either after a finished review is read again too (a years-in-business entry made after the review leaves its item for the agent to tick), with Luna's earlier items replaced in place by info notes. NTL and GL (`coverage.ntl`, `coverage.gl`, `coverage.hasGl`) are Luna's own questions, not form coverage: setting them is no edit. The panel compares what Luna read with key order ignored (`stableJson`): chrome.storage gives the intake back with its keys sorted, and reopening the panel isn't an edit either. The same holds for the key a Luna answer is tied to (`assistContextKey`). NTL has its own flag; "coverage change" means any other change. The usage log records counts only (`ai_suggest`, page `ClaimsBox`, with the same token and cache counters as page reviews).

Since 2026-10-10 the same call also answers, per line, whether it says the client has, wants or asks about general liability (`generalLiability`: GL, CGL; a line saying they don't is false). GL is its own question like NTL: neither is sent in `formCoverage`, a line asking for GL is not a coverage change, and setting either in the panel doesn't make Luna read the box again. Progressive's other business coverages are filled None of the above unless the notes say the client has GL (`coverage.hasGl`; GL asked for on the form, `coverage.gl`, doesn't change them: TNI, 2026-10-19), so when a line is flagged, code adds one Intake check item (`ai.gl`) for the first such line, whether or not the form's GL box is ticked. Its evidence is the line itself: code split it from the box and checks the flagged line is one it sent, so Luna can't supply a quote of its own. The card quotes the line (shortened past 120 characters) and offers **Client has GL**, which sets `coverage.hasGl = true` as the agent's edit (the client has GL; `coverage.gl` stays a request to quote GL, which puts the General Liability item on Rates; `coverage.hasGl` changes nothing there) (the same path as an edit in All client details: saved with the intake, listed in `agentEdited`, logged as `intake_edit` without the value; those questions are then left to the agent), and **Not GL**, which only checks the item. Without Luna (assistance off or no key), or when the review fails, nothing changes: other business coverages stay None of the above unless the agent sets `coverage.hasGl` in All client details.

Driver gender is filled MALE (TNI standard) unless `drivers[i].gender` is set. Once per intake, with assistance on and the key set, a sibling call (`reviewDriverNames`, response format `driver_first_names`) asks whether each driver's first name is more often given to women. It sends **only first names**: the first word of each first-name field (letters, apostrophe or hyphen, two to thirty characters; initials are skipped), keyed `d<index>`, for drivers whose gender isn't set, at most 20. No last names, dates of birth, license data, business name or any other intake field go with them, and the claims-box and page reviews still replace names with `[client]`. Luna answers each with a bounded enum, `likely_female`, `likely_male` or `unclear`, never free text; a missing, extra or out-of-list answer fails the whole check. For `likely_female` on a driver whose gender is still unset and whose name is still the one sent, code adds an Intake check item (`ai.driver-gender`) that says gender is filled Male, names the first name, and says it's a guess from the name only. **Use Female** sets `drivers[i].gender = 'FEMALE'` and **Keep Male** sets `'MALE'`, both as the agent's edit. `likely_male` and `unclear` add nothing. A failure adds an info note (the TNI standard stands) and is tried again when the assistant settings change; an answer for names edited meanwhile is dropped and the names read again, and a first-name edit after a finished check retires its items in place and asks again. The usage log records counts only (`ai_suggest`, page `DriverNames`). Without Luna nothing is sent and gender stays Male unless the agent sets it.

The buttons on these cards come from code (`GL_CHOICES`, `genderChoices`), and the panel only applies a choice that is on its stored item, for that item's own field, and one of the allowed values (`coverage.hasGl` true; `drivers[i].gender` FEMALE or MALE).

With assistance on, this leaves the computer: the unresolved questions with their labels, sections, current values and option texts as the page shows them (unredacted, since the answer must be one of them), the carrier-scoped TNI rules, and the scoped intake (`scopedIntake`): the applicant, operations, garaging, coverage, claims, additional notes, trailer and prior-insurance sections and the active driver, vehicle and trailer. Identifier keys (VIN, license and plate numbers, FEIN, phone, email, account numbers) are removed and USDOT/MC become presence booleans; every remaining string is redacted with the claims-box review's term list (`redactionTerms`, `[client]` for the client's and owners' names, drivers' names and dates of birth, the garaging street, unit, city and ZIP, and contact and ID numbers), in the first call's evidence sources and in the verification call's intake alike. What still goes, in clear: the applicant's year established, years in business and of experience, whether the owner drives, the 60-day USDOT/MC answer and the application date; the garaging state; business class and every operations answer (what they haul, radius, ELD and its brand, SR-22, filings and which, hazmat and placards, moving state, team driving / slip seating, loads to Canada, personal use, vehicle ownership, equipment value); every coverage choice and limit; the whole trailer section (ownership, hitch, interchange and its limit, trailer equipment value); vehicle and trailer type, year, make, model and value; the active driver's license state, CDL, CDL year, marital status and gender when set; prior insurance (type, carrier, limit, expiration) and the computed `priorPolicyExpired` and `noPriorInsurance` (the carrier says "NO POP", "No", "None" or "N/A" with no expiration date); and the claims box and notes with the terms replaced, with `hasClaims` and the NTL flag. The redaction is the same as the usage log's and has its limits: a value is replaced only where it appears as written in the intake's field, so the same date, phone or name written another way in the claims box or notes (1/2/1980 for 01/02/1980, (555) 123-4567 for 555-123-4567) is still sent; a term shorter than three characters is kept; and a single name word is replaced only as a whole word ("Ann" leaves "Annual", "Car" leaves "Cargo"), but a whole word shared by a name and a fact (a business called "Expediter Services") redacts the fact too. The prior carrier's name is not a term and is sent. Drivers' first names are the one exception to name redaction: the driver-name check above sends them, alone, in their own request (first word only, nothing else from the intake). Without the OpenAI key, deterministic rules still work and unresolved questions stay with the agent. OpenAI `store: false` does not imply zero retention under the provider's other policies.

```mermaid
flowchart LR
    A[Unresolved choice questions] --> B[Drop never-list and agent-settled questions]
    B --> C[Luna: option or leave, plus cited evidence]
    C --> D[Luna: second call checks evidence support]
    D --> E[Agent accepts; Luna may make separately opted-in automatic picks]
    E --> F[Page unchanged since the request? Apply and verify retained value]
    F --> G[Automatic picks wait for approval before Continue]
```

## Enforced behavior and its limits

- The never-list filters question text for MVR/CLUE, exclusions, signatures/attestations/authorizations, bank/card/SSN/password details, and typed identifiers. A DOT-lookup identity mismatch is review-only. A question the rules leave to the agent as a client fact or attestation (`source: 'fact'`/`'attestation'`, or a `clientFact` rule the intake doesn't answer, such as marital status or vehicle ownership) carries `manualOnly` on its fill-report item, and `collectItems` keeps it from Luna entirely: no suggestion and no automatic pick. If the same control appears in multiple report groups (for example, an invalid prefilled answer also missing an intake fact), manual-only and review-only restrictions survive deduplication regardless of report priority. It filters questions; what the intake context contains is set by `scopedIntake` (above), whose redaction leaves business and coverage facts in clear.
- Questions the agent changed, or that an applied AI answer already settled on this page, are not sent again.
- The answer must be one of the page's current options or `leave`. Luna uses strict structured output and validates its option and source IDs; missing evidence, invalid output, or an unsupported choice becomes `leave`. The cited source must be one of the supplied intake facts or carrier rules.
- A second Luna call verifies that the cited evidence supports the proposed option. Both calls are required for any non-`leave` result, use the fixed `gpt-6-luna` model, and stay within the adaptive request and output budgets above.
- Luna automatic selection is opt-in through `lunaAuto`. It has no probability or confidence threshold: only a successfully verified, source-supported choice from the fixed `gpt-6-luna` model can be selected, and the field must be a visible/applicable radio, select or checkbox with a changed value outside the manual-only safety list. The second call is another judgment from the same model, not calibrated accuracy evidence.
- Before anything is applied, the panel compares the page with the snapshot taken when the request started (every control's current value). Any change, including an agent edit made while the request was pending, cancels the apply and asks for a fresh fill. `answer()` then checks the field's kind, section, options and current value, and that the page kept the answer. An agent edit while the answers go in keeps the agent's value on that question, protects its key from later fills, and stops the answers still to come, across all frames, including an edit in a frame that is waiting its turn or already finished (remaining answers are reported as not applied, with the reason); the recorder reports that edit as the agent's when the apply ends. Every dispatch checks the original guard session and current intake context, so a replaced frame document or changed intake stops remaining answers. Guarded edits remain protected in their original intake, tab, and vehicle/driver/page scope after a switch, including transport failures; only keys are retained. Intake replacement keeps those separately scoped records, while explicit Clear erases the current intake's records and prevents its late writes from restoring them without cancelling another intake's guarded edits ([browser filling](browser-filling.md)).
- Automatic picks are marked purple and hold Continue until the agent approves them: Approve or Reject in a pick's row, or the dock's Approve for all of them, which reads "Approve and continue" only when they are all that is left on the page. A suggestion (not put in) shows in its question's row with Use this answer and No thanks. A durable hold is recorded before answer dispatch, so intake/cache replacement or a transport failure after dispatch cannot erase it. A guard-read failure before the first answer is sent removes the preparation holds; a failure after any answer is sent retains the conservative holds for review. A trusted manual correction before Reject releases that hold; otherwise Reject keeps it until the agent changes that field or explicitly confirms the current page answer. Identity-bound pending holds survive panel reload and follow the physical quote across intake changes. They retire when the exact quote URL changes or the originating document is proven replaced or gone; a changed value in the same document remains a review hold. Picks made before intake edits or a driver/vehicle change stay listed (labelled); approval re-checks that the page is unchanged since the pick was applied, otherwise the pick stays unresolved for review. Durable pending records contain redacted display text and fingerprints, not intake copies or API keys. Approval and current-answer confirmation check the originating frame, document, question and expected value fingerprint, so a matching answer in another frame cannot release a hold and redacted names do not prevent review. Duplicate questions across frames are left for the agent before applying. Replacing or clearing the intake, changing the quote URL or evicting a cached pick invalidates in-flight approval callbacks. Ordinary agent-edited field keys also survive panel reload, scoped to the intake, tab and page, without saving typed values.
- Cached answers are keyed on the question as the page shows it (key, label, section, options, current value, status), the intake and active driver/vehicle, the model and the policy version. Luna's optimized path keeps the same local answer cache and does not enable an extended paid API cache. Late responses after a page or context change are discarded.
- Luna returns data and has no navigation or submission tool. Page content and intake text are data, not instructions.
- On a carrier's stop page, on a step that is the agent's (`stopSteps`: GEICO's Final Quote Details, MVR & CLUE and Payment Information), and on a screen that is (`stopButtons`: GEICO's Add USDOT Number), Luna isn't asked and nothing is applied: `aiActionCurrent` refuses through `stopNoteFor`, and `answer()` puts nothing in while the page shows one of the stop steps the fills in that document were given.
- Successful Luna reviews report `tokensIn`, `tokensOut`, `modelCalls`, `reasoningTokens`, `cachedTokens`, and `cacheWriteTokens`. Reasoning tokens are included in the output count. `modelCalls` counts logical provider calls and excludes HTTP retries. These counters do not account for all possible spend from failed or timed-out requests.

The AI never-list does not override deterministic carrier rules: Progressive answers its driver-exclusion question No for a driver listed on the intake and Yes for one the intake marks excluded. See [intake and rules](intake-and-rules.md) when changing that behavior.

## Making changes

Keep the written [TNI rulebook](../src/ai/tni-rules.js) aligned with implemented carrier standards and each rule's `source` ([intake and rules](intake-and-rules.md)): the rulebook states coverage and workflow standards, never a default for a client fact. It has sections for Progressive and AmWINS only: `evidenceFor` in [common.js](../src/ai/common.js) splits it at the AmWINS heading and gives any other carrier no TNI rules. TNI's GEICO standards (2026-10-21) are filled by GEICO's own rules and are not in the rulebook, so on GEICO Luna's sources are the scoped intake alone; a GEICO section would need that split changed as well. A fact the intake doesn't give (marital status, year established, current-carrier tenure, loss runs, the vehicle registrant) is the agent's, and Luna must not cite a standard for it. The exceptions are TNI's 2026-10-10 standards: gender MALE unless set in client details, year licensed = birth year + 17 (the agent's without a readable date of birth), continuous coverage Yes when the intake shows current insurance, and other business coverages None unless the notes say the client has general liability ([intake and rules](intake-and-rules.md)). For-hire answers follow the business class, not the MC number. A new client fact or agency decision needs evidence; model output and agent acceptance rates do not establish correctness. Luna suggestions and automatic selection remain opt-in and subject to the approval hold. Keep exact mappings, calculations, and execution in code; use the model only for the bounded semantic choice that remains.

Test invalid options, missing or misleading sources, restricted questions, stale responses, manual edits, model identity and approval-before-Continue when those paths change. Preserve a `leave` result when evidence is missing. `npm run mock:luna` drives the packaged extension against controlled OpenAI responses and checks key isolation, automatic-selection setting, approval hold, rejection/manual correction, conflicts, stale responses, retired-assistant pending holds, and that facts left to the agent (`manualOnly`) never reach Luna; the agent dismisses those facts on the fixture page so only the Luna approval holds Continue. Mocked responses prove integration behavior, not live accuracy or latency. Use [testing](testing.md) for harness setup.

The evaluation runner (`npm run ai:eval`) supports offline `--score <saved-result.json>` and explicit Luna-only live mode with `--live`. Live mode uses `OPENAI_API_KEY`, separately from extension settings, and is never run as part of unit or browser tests. The evaluation agent decides whether a live run is warranted. Committed cases are sanitized synthetic scenarios with `expertReviewed: false`; their proposed expected answers are not an expert answer key. Reports distinguish suggestions, abstentions, evidence paths, errors, timing and token usage; no output establishes calibrated automatic thresholds or live accuracy. Saved result case IDs must be unique; duplicate IDs are rejected before scoring.

Usage includes `ai_suggest` (model, timing, counts, provider usage, errors; a page review's error text passes the intake redactor first) and `ai_decision` (redacted label, decision, chosen option, evidence basis). The key and client values are never logged. Reports summarize acceptance and failures; this does not train the model or promote rules automatically. Read [learning](learning.md) only if changing that feedback mechanism.

## Proposed work, not current capabilities

Potential extensions include confirmed extraction of free-text requests, a final requested-versus-entered check, AI-drafted rule proposals for human review, promoting repeatedly verified choices to deterministic rules, and centrally managed provider access. These are not committed milestones or permission to expand a task. Validate each against actual quote correctness, not acceptance rate alone.
